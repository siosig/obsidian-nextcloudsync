# Nextcloud Sync — Specification

This document is the single source of truth for the plugin's current behaviour. It is a snapshot of the complete current specification in one file, and it is rewritten in full whenever the behaviour changes. The tests under `tests/` verify it, and the test clause IDs (`CN-*`, `UP-*`, `CF-*`, `FR-*` and so on) correspond to the catalog in `tests/a-no-nextcloud/spec-coverage/clauses.ts`. It describes WHAT the plugin does (contracts, defaults, test clauses); HOW it is implemented is described in docs/plan.md. Setting keys, type names and command ids are kept in English.

---

## §1. Overview and goals

A bidirectional sync plugin that puts data safety first (zero file corruption, no endless multiplication of conflict files, no unintended loss). It uses standard WebDAV as its core and transparently enables Nextcloud extensions. It supports both desktop and mobile (iOS/Android).

**Main problems it solves**: the unreliable-mtime problem / file corruption on network disconnection / loss caused by misdetected renames / endless multiplication of conflicts.

## §2. Terminology

State DB (the state at the time of the previous completed sync = Base) / Local / Remote / atomic update (tmp -> rename) / `oc:checksums` (SHA-256/SHA-1) / `oc:fileid` (immutable ID used for rename tracking) / `deviceId` (UUID v4) / `sync-token` (RFC 6578 incremental sync) / IgnoreList (suppresses self-triggered events).

## §3. Architecture (progressive enhancement)

- The transport layer is abstracted behind `IWebDAVClient`. `WebDAVFactory` chooses between `NextcloudClient` (extended) and `StandardWebDAVClient` (standard fallback) based on **what the probe responses contain** (`SD-1` to `SD-3`). The decision expression is as follows, and **whether an exception was thrown is never used as evidence**:
  - `isNextcloud = (capabilities returns 200 AND ocs.data can be read) OR (status.php returns 200 AND productname matches /nextcloud/i)`
  - **capabilities is the primary evidence** because it is the very source of `hasChecksums` / `hasFilesLocking` / `hasBulkUpload` / `version`. Setting `isNextcloud: true` for a connection where it cannot be read would be hollow. **`status.php` is the secondary evidence**: a rescue so that a legitimate Nextcloud whose OCS endpoint is blocked with 401/403 is not misclassified (it answers without authentication).
  - If `isNextcloud === false`, `StandardWebDAVClient` is used and the Nextcloud-only features (chunked upload, version history) are disabled. **No new user-visible setting is added** (internal normalisation only).
  - **A public-link share (`/public.php/webdav/`) is classified as standard WebDAV as a consequence of the general rule** (both probes return 404 because of the probe base URL). No special case that embeds the URL shape in the decision is provided.
  - **ownCloud is intentionally still treated as Nextcloud** (OCS answers, so the primary evidence yields true). The reasoning: do not remove features from existing users without a way to verify against a real instance.
  - **Maintenance mode is handled before the decision**: it is thrown as `MaintenanceModeError`, and the `WebDAVFactory` catch **rethrows it**. Previously a bare catch swallowed it, so even during maintenance the plugin fell back to standard WebDAV and the user only saw `HTTP 503 (PROPFIND)`.
  - **A probe that is rejected at the network layer is not used as evidence.** The absence of a response is not proof that the server is plain WebDAV, so, as before, it falls through to a retry with `StandardWebDAVClient` to preserve resilience (detection is separated from resilience).
  - Verification: `SD-1`/`SD-2` (layer a, case table D-1 to D-7) and `SD-3` (**layer b-4**, degraded behaviour against a real Apache `mod_dav`).
- When Nextcloud is detected, `oc:checksums` / `oc:fileid` / WebDAV Sync are enabled. Without Nextcloud, the standard fallback uses ETag, size and mtime.
- Uploads go through `IUploadStrategy` (`SimpleUploadStrategy` / `ChunkedUploadStrategy`).
- For the layer structure see docs/plan.md §19. **`requestUrl` is mandatory** (`fetch`, Node `http` and `fs` are forbidden; for mobile compatibility, I/O goes through `app.vault.adapter`).
- **Single source for connection values**: the WebDAV endpoint is derived from the canonical value returned by the login flow. An optional subfolder at the end of `serverUrl` is the only way to change where the vault is placed (a contract shared by `.env` / E2E env / both WebDAV clients / remotePath; in line with the project's design policy of minimising user freedom). That subfolder must already exist on the server; the plugin does not create it (§11.2).

## §4. Change detection

> For the details of the implementation logic (remote/local scanning, hash optimisation, the per-file four-quadrant decision) see docs/plan.md §4 to §7.

### §4.1 Remote (`oc:checksums` priority chain)
`PROPFIND` fetches `getetag` / `getcontentlength` / `getlastmodified` / `sync-token` / `oc:checksums` / `oc:fileid` in one request. Priority for determining `remoteId`: (1) `oc:checksums` SHA-256 (`sha256`) -> (2) ETag (`etag`) -> (3) size (`size`). **SHA-1 is not used** (the PROPFIND parser extracts only `SHA256:`; the value `'sha1'` remains in the `RemoteIdType` type but is not used to determine remoteId).

### §4.2 Local (mtime -> SHA-256)
**mtime is not used as a decision condition.** mtime is only a first-pass filter for "should a hash be computed". The final decision compares SHA-256 with the State DB `localHash`.

### §4.3 Rename detection
Matching `oc:fileid` with a different path -> rename confirmed (reflected as MOVE). Without Nextcloud, it falls back to searching for a pair with the same size AND the same SHA-256.

### §4.4 Performance optimisation
- The **stat signature** (mtime + size) is persisted and used for the "unchanged" fast path. Size alone is insufficient (there is a time-window hash fallback). `mtime` is kept separately from the signature. Backward-compatible migration exists.
- The initial sync reuses a single scan and compares sizes first. **Files larger than 20 MB (`MAX_HASH_SIZE`, a hard-coded constant in `src/util/limits.ts`, not a setting) skip the local pre-hash** (the hash is computed lazily at upload time).
- If the server SHA-256 matches the baseline, no re-hash is needed (except for just-uploaded files).
- The state store uses compact serialisation, debounced flush and a remote-id index for O(1) lookup.
- **Root-ETag short-circuit (§8a.5)**: the full scan that F1 runs every time is replaced by the list rebuilt from the StateDB for as long as the vault root ETag matches the previous real scan, which saves the infinite-depth PROPFIND (Nextcloud only, no change to deletion safety, self-healing).

## §5. Sync flow and triggers

> For the details of the implementation logic (entry points, overall orchestration, change-detection strategy, concurrency and memory budget) see docs/plan.md §2 to §5 and §11.

### §5.1 Capability detection
`GET /status.php` (maintenance check) -> `GET /ocs/v1.php/cloud/capabilities?format=json` (header `OCS-APIRequest: true`) -> build `NextcloudFeatures` -> choose the client.

### §5.2 Initial sync (the Dry Run modal was removed)
- **The Dry Run approval modal was removed.** The initial sync runs without an approval gate (the logic is retained; an unconfigured state and concurrent runs are handled safely).
- Initial sync = capability detection -> SHA-256 of all local files (optimisation: §4.4) -> full remote PROPFIND scan -> reconciliation -> execution -> build the initial State DB (storing the sync-token).
- Even in the **fresh-install state** (no vault folder on the remote), `connect()` succeeds and the first upload creates the hierarchy (handling of missing parents: §18 F2). **Only for the initial sync (empty State), a 404 on the root is read as an empty listing.** Tests: `INIT-1/2/3`, `VRR-4`.
- **A root 404 and an "empty listing" are different signals (GitHub issue #50).** When the vault folder itself does not exist, `getFiles('')` throws `RemoteRootMissingError` (a subclass of `NetworkError`, status 404), while a 404 on a subpath still returns `[]` as before (in the recursive scan of plain WebDAV, a subfolder that disappeared midway is also still treated as an empty subtree). A 207 with zero children is the server's truth "the folder exists but is empty" and flows straight into the absence deletion of §8. **When a tracked vault (non-empty State) receives a root 404, it is re-seeded rather than deleted** (§8). Test: `VRR-7`.
- **Even on a 207, if the body cannot be read, an error is thrown (GitHub issue #51).** `getFiles` / `getDirectories` / `statFile` / `getChanges` throw `RemoteListingUnreadableError` (a subclass of `NetworkError`) when the response is a 207 but the body is not a well-formed `DAV:multistatus`; they never return an empty array, `null` or an empty change set. The check is centralised in `parseResponses` / `readMultistatus` of `src/network/dav/propfind.ts`, and every call of both clients (`NextcloudClient` / `StandardWebDAVClient`) goes through it. An empty body, a parser exception (`@xmldom` in the test layer), a browser `<parsererror>` document, and a root element that is not `multistatus` are all judged "unreadable", while a legitimate `DAV:multistatus` (including one with zero responses) passes as before. The check does not react to user data (the text of href and displayname). `getRootEtag` / `isRemoteDirEmpty` still return `null` / `false` for an unreadable body as before (the safe side is unchanged; running the check makes that safety explicit in the code). Diagnostics are condensed into one error-message line (call name, path, HTTP status, body byte length, reason, and a fragment of the first 256 characters of the body) and never carry the whole body. Tests: `ULG-1` to `ULG-18` (layer a).

### §5.3 Steady-state sync (differential + three-way comparison)
- Differences are fetched with WebDAV Sync (REPORT + sync-token). HTTP 410 (token expired) or no stored token -> fall back to a full scan. **Note: if the server does not support sync-collection (415), it always does a full scan (§18 F1).**
- **Three-way comparison (Base/Local/Remote, hashes only)**:

| Local vs Base | Remote vs Base | Decision | Action |
|---|---|---|---|
| Equal | Equal | Unchanged | None |
| Different | Equal | Local Modified | upload -> update Base |
| Equal | Different | Remote Modified | atomic download -> update Base |
| Different | Different | Conflicted | §6 |

- **When no Base exists (GitHub issue #23)**: the absence of a record must not be taken to mean "locally unchanged". `processRemoteFile` **always checks whether the local file exists** and classifies as follows (aligned with the initial sync `buildInitialPlan`).

| Local file | Additional condition | Decision | Action |
|---|---|---|---|
| Absent | — | New remote | download |
| Present | The server checksum exists and equals localHash | Converged | seed State with **no transfer** |
| Present | Content differs, or identity cannot be confirmed (etag/size only) | **Conflicted** | §6 (`.md` is merged). **The strategy is not switched because Base is missing** |

  > Before the fix, when base was missing `localChanged` was always false, so the case fell into `Remote Modified` and the download silently overwrote the local file (data loss). **ETag is not used** for the identity check because it is an opaque, server-implementation-dependent value that cannot be reproduced from local content, and a wrong decision would reintroduce the silent overwrite. Tests: `UBC-1` to `UBC-9`.
  >
  > **When the push fails during conflict resolution**: if the merge result could not be pushed to the server, `resolveByWrite` **does not record the merged body as localHash** (it keeps the previous baseline and attaches no stat signature). If it were recorded, the next sync would read "Local equal, Remote equal" as converged and clear `isConflicted`, so the merge result would stay stranded locally and never reach other devices (the older measure `G1-1`, which merely set `isConflicted`, cannot prevent this). Test: `UBC-7`.

- **Contract for creating parent collections**: a WebDAV PUT does not create parent collections automatically, so an upload to a folder that does not exist yet does MKCOL on the ancestors and then retries exactly once (reactive; this is designed to save one round trip in the general case of an existing folder, and is deliberately **not** proactive). This path satisfies the following rules.
  1. **Single-flight**: for the same remote directory path, at most one MKCOL is in flight at a time. N uploads that need the same ancestor share the one in-flight request and wait for it. **Rationale**: uploads are serialised per *immediate parent* directory (`serializeByDir` in `runFileBatch`), so `F/a.md` and `F/sub/b.md` run on different chains = in parallel, and they used to compete for the MKCOL of the shared *ancestor* `F`. Nextcloud returns **423 Locked** to the losers because of the lock held while a collection is being created (measured: `[201, 423, 405, 423]` with four concurrent requests).
  2. **Only proof of success is remembered**: only when MKCOL returned **201 (created) / 405 (already exists)** may the "already created" cache be populated. Anything else (409 / 423 / 401 / 403 / 5xx / an exception) is not remembered and stays in a state where the next request can issue it again. **Failures are not remembered** (there is no negative cache).
  3. **Failures propagate and do not descend**: if a level cannot be created, `RemoteDirCreateError` (derived from `NetworkError`, holding the path and status of the failed *level*) is thrown and the levels beneath it are not attempted.
  4. **Handling per caller**: the missing-parent handlers of `uploadFile` / `uploadChunked` / `moveFile` **swallow the ancestor's failure and retry the PUT/MOVE once**, and surface the ancestor's error only when that retry also fails (so as not to break setups where the folder really exists and only MKCOL is rejected with 403). `createDirectory` **throws on failure** (this closes the path where watch would start tracking a folder that does not exist on the server). `createVaultRoot` keeps swallowing ancestor failures **best-effort** (the 201-vs-405 result of the immediately following `mkcolStrict` is the arbiter for the §5.2 decision, and a transient ancestor failure must not lose that answer).
  5. **Boundary of retries**: `moveFile` also retries MOVE **exactly once** after the MKCOL when the parent is missing (404/409). This is a **different layer** from the "no retries for write requests" rule of §5.6a (the transport-layer automatic retry when no response was ever received; forbidden because the server may have processed the request successfully before the timeout), and is application-level recovery from a definite response that the server returned. Conversely, when the MKCOL **never got a response** (timeout and so on), no retry is made — the parent certainly does not exist, so it would only spend one more timeout and receive the same 404.
  - The above is identical in both clients (`NextcloudClient` / `StandardWebDAVClient`). Discarding a stale positive (recovery after another device deleted the folder) also takes the same form in both clients and for both PUT and MOVE. `MSF-1` to `MSF-16` verify it.
- Round-trip reduction: file-locking is OFF by default, **If-Match optimistic locking** prevents lost updates, reactive MKCOL, blind delete. **Bulk multipart upload is not wired**: the upload strategy selector chooses only Simple/Chunked. The **unused `bulkUploadEnabled` setting and the threshold constants in `limits.ts` (`BULK_MAX_*`) were removed** (both were dead code with no consumer). The server capability probe `hasBulkUpload` (`capabilities.dav.bulkupload`) is still fetched in connect() as progressive enhancement and carried in `NextcloudFeatures` (for deciding when bulk is implemented in the future; currently unconsumed).

| Trigger | desktop | mobile |
|---|---|---|

| Sync on edit (watch) `watchOnChangeEnabled` | Default true (about 2 seconds debounce after editing stops). **File and folder create / modify / delete / rename are propagated immediately**: for files, create/modify -> **single-file sync (§5.7 below)**, delete -> **remote deletion (to the trash) with a safety decision**, rename -> MOVE; for folders, create -> MKCOL (idempotent), delete -> collection deletion (tracked folders only, to the trash), rename -> MOVE (all immediate, no debounce). ### §5.5 Concurrency guard and recovery from connection failure (`CONC-1`)

- **Balking guard**: a full sync is limited to one at a time by the `running` flag (watch mode / periodic sync / manual runs do not collide). If another sync arrives while one is running, it returns early with `sync: skipped — already running`.
- **A connection failure must not leave `running` stuck**: in the session body (`runSyncSession`), **`ensureClient()` (client creation + capabilities fetch) runs inside the try/finally**. Even if ensureClient throws or hangs, (1) the `finally` always resets `running=false` (so the next sync can recover), and (2) the `catch` surfaces the real error as `sync: FAILED` through the log and a Notice (it is not swallowed).
  - **Background of the regression**: `ensureClient()` used to be outside the try, so on a connection failure the `finally` was never reached and `running=true` stayed stuck forever; every later sync was rejected as "already running", the startup sync re-triggered the same failure at every restart, so recovery was impossible (and the real error was not logged either). Moving `running=false` to the start of the finally did not help because ensureClient itself was still outside the try, so this path remained.
  - Test: `CONC-1` (`tests/a-no-nextcloud/sync/concurrentSync.test.ts` — verifies that when ensureClient throws, `running` is released, a `sync: FAILED` log is written, and the next `syncManual` can run again).

### §5.6 Network request timeout (`NET-1`)

- **Every WebDAV request gets the `networkTimeoutSeconds` timeout (default 30 seconds).** Both clients (`NextcloudClient` / `StandardWebDAVClient`) and `remotePath.ensureRemoteDir` do not call Obsidian's `requestUrl` directly; they go through the **common wrapper `requestUrlWithTimeout(params, timeoutMs)`**.
- **Reason**: Obsidian's `requestUrl` has neither a timeout nor an `AbortSignal`, and **waits forever** for an unresponsive server (half-open socket, stalled proxy and so on). The sync holds the `running` guard across its awaits, so one hang prevents the finally of §5.5 from being reached and can lock the engine permanently. The wrapper races a timer (like `Promise.race`) and rejects on expiry (the original `requestUrl` continues but its result is ignored), and the guarded try/finally of §5.5 handles it as an ordinary failure (`sync: FAILED`, Notice, release of `running`, retry next time).
- **`timeoutMs <= 0` (that is, the setting 0) means unlimited** (an intentional escape hatch for slow, high-latency links). `networkTimeoutSeconds` is read live on every request, so a setting change takes effect from the next request.
- **Background of the regression**: `networkTimeoutSeconds` existed in the types and the settings UI but was a **dead setting that was never wired to any real request** (it is now activated).
- Test: `NET-1` (`tests/a-no-nextcloud/network/requestWithTimeout.test.ts` — resolves on completion, rejects with timeout on a hang, propagates lower-level errors, unlimited with `0`).

### §5.6a Automatic retry of read WebDAV requests (`NET-3`)

- **Background**: on a real Android device, immediately after returning to the app from the browser round trip of Login Flow v2, only the first WebDAV PROPFIND reached the `networkTimeoutSeconds` timeout because of a transient hang in the device's HTTP stack (equivalent to a stale connection). This was confirmed by measuring the nginx access log of the test server. The server and the network path were healthy (the request had not even reached nginx, and the immediate retry succeeded instantly).
- **Response**: both `NextcloudClient` and `StandardWebDAVClient` gained `reqReadonly()`. **Only read requests (PROPFIND/GET)** are automatically retried up to 2 times with `withRetry(..., 2, 1000, () => true)` when `req()` (a thin wrapper of `requestUrlWithTimeout`) rejects. `req()` always calls `requestUrl` with `throw:false`, so it rejects only when "no HTTP response was received at all"; statuses such as 401/404/415 stay on the normal path where the caller judges `res.status`, which means **non-transient errors never even reach this retry layer**.
- **Write requests (PUT/DELETE/MOVE/MKCOL/PATCH/LOCK/UNLOCK) are not retried.** On a timeout the server may actually have processed the request, and a blind retry would cause double processing or a false detection of a lost MOVE source. They fail immediately as before and leave convergence to the next sync (self-healing).
- **REPORT (`getChanges` / `getSyncToken`) is semantically a read but is explicitly out of scope.** If REPORT fails, the existing path that falls back to a full-scan PROPFIND is itself covered by the retry, so there is no functional gap.
- The number of retries is limited to **2** rather than the `withRetry` default of 5, so that the worst-case duration of one request stays within `timeoutMs x 3 + about 3 seconds of backoff` (about 93 seconds with the default `networkTimeoutSeconds` of 30), avoiding the experience of an apparent multi-minute hang during a real disconnection.
- Test: `NET-3` (`tests/a-no-nextcloud/network/standardWebDavClient.retry.test.ts` and `tests/a-no-nextcloud/network/nextcloudClient.retry.test.ts` — for read requests, a timeout once then success is retried successfully, and three consecutive failures throw the original error unchanged; write requests, REPORT and non-transient resolved responses (such as 404) are not retried and `requestUrl` is called only once).

### §5.7 Single-file sync in watch mode (`WSF-1` to `WSF-10`, GitHub issue #23)

**The single-file processing of watch mode ("Sync on file change") goes through exactly the same decision and resolution path as a full sync.**
The watch side has no classification or conflict-resolution logic of its own (the implementation is not duplicated).

- **Fetching the remote state (`WSF-1`)**: `IWebDAVClient.statFile(path)` (**Depth:0 PROPFIND**) fetches the remote state of the one target file.
  File present -> `RemoteFileInfo` (same field semantics as the full-sync listing), 404 -> `null`, a collection -> `null`,
  any other non-207 -> throws `NetworkError` (**so that an ambiguous failure is not misread as "does not exist" and blindly created or overwritten**).
  **Even on a 207, if the body cannot be read, `RemoteListingUnreadableError` is thrown** (not `null`).
- **Classifying an edit (`WSF-2` to `WSF-4`)**: `syncSingleFile(path)`
  (1) defers if a full sync is running (see below); (2) finishes with **zero communication** if the content is identical to base (signature fast path -> hash comparison);
  (3) uploads as new if `statFile` returns `null` (no precondition); (4) otherwise delegates to the **same three-way comparison as `processRemoteFile`**.
  Therefore upload / download / conflict resolution (`.md` is merged) / If-Match (412 -> switch to conflict) / size limit / marker re-entry prevention /
  the untracked-both-sides rule (§5.3, when no Base exists) **all apply identically to a full sync**. Communication errors are put on the retry queue and converge at the next sync.
- **Safety decision for deletion (`WSF-5`)**: `deleteSingleFile(path)` delegates to **the same `DeletionService.deleteLocallyMissing` as a full sync** (shared; everything from `statFile` onward is not decided on the watch side, and `WatchOperations` keeps only the path lock, the `isSyncRunning()` exclusion, and persistence/notification).
  It deletes only when the checksum recomputed on the server equals base, and **if they differ it does not delete the remote and restores the file locally**.
  If no checksum can be obtained, it does not delete. If the remote does not exist, only the tracking (state / merge base / clean-side snapshot) is cleaned up.
- **Folder deletion is also exclusive with a full sync**: `deleteSingleFolder(path)` has the same early return on `isSyncRunning()` as `deleteSingleFile`. It was the only one lacking this exclusion although it is the most impactful sink, issuing a recursive `deleteCollection` (a path existed where a running scan itself trashes a folder, and the plugin reacts to that vault event by firing a collection DELETE without proof).
- **Converged form after an upload (`WSF-6`)**: after a successful upload, the `FileState` has `localHash === remoteId`, `idType === 'sha256'` and
  `isConflicted === false`. Both upload strategies send `OC-Checksum: SHA256:<localHash>` and the server returns it,
  so this matches the real remote identifier. **The next sync converges with no communication and no transfer** (the old implementation recorded the `remoteId` from before the PUT,
  so it misjudged "the remote changed" every time and re-downloaded the file it had just uploaded).
- **Exclusion with a full sync (`WSF-7`)**: while `running`, a single-file sync performs no I/O and defers to `watchPendingPaths` (memory only),
  re-evaluating after `syncManual` completes (the same path collapses into one). **Deletions are not deferred** (the full sync detects the missing local file and handles it).
- **Notification (`WSF-8`)**: a `Notice` is shown only on errors and **when a conflict was touched** (the three cases — marker written / clean merge /
  settled by a deterministic strategy — are worded differently). Ordinary upload / download / no-change with no conflict is silent.
  Settlement by a deterministic strategy is indistinguishable from an ordinary transfer in the `uploadedCount` / `downloadedCount` totals, but because **the content of one side is discarded** it is detected by the difference in the number of `handleConflict` calls and always notified.
- **Path equivalence (`WSF-9`)**: from the same initial state, the final state (local content, remote content, `FileState`) after one `syncSingleFile` equals that after one `syncManual`.
- **No re-sync from its own writes (`WSF-10`)**: downloads / merge writes on the watch path are excluded by `isOwnSyncEvent` in `main.ts` through the ignore registration of `LocalAdapter`, and do not trigger a new single-file sync (no PUT -> event -> PUT loop).
- **Background of the regression**: the old implementation did neither a PROPFIND nor a base comparison, and because of the synthetic `RemoteFileInfo` with `etag: null` it **did a PUT without even attaching If-Match**.
  On this path, which is ON by default on desktop, edits from other devices vanished with no conflict, no merge and no notification (the re-report of issue #23).
  The fix for the classification of the full sync (when base is missing) had addressed only the full-sync side, and this path was left unfixed.

> **The default of the concurrency `networkConcurrency` is derived from device RAM (shared by desktop/mobile, no platform branching)**. `resolveConcurrencyDefault(deviceMemoryGB)` (`src/util/limits.ts`): unknown RAM = **3** / >=4GB = **8** / >=8GB = **16** / less than that = **4**. The `16` in `DEFAULT_SETTINGS.networkConcurrency` is only the default value in the type, and it is overwritten with the RAM-derived value on the first `loadSettings()` (when there is no stored value). Stored values of existing users are unchanged. On mobile `navigator.deviceMemory` is often absent, so the effective value tends to be **3**.

### §5.7b Serialising watch cycles and protecting the file being edited (`WOV-1`/`WOV-2`, GitHub issue #42)

**Watch cycles for the same path are serialised. Also, a remote -> local write is deferred
while that file is being edited.**

**Background (the failure that actually occurred)**

A report against 1.0.0 (issue #42) said that "characters vanish while typing, formatting breaks, and a block of conflict markers is inserted into the body".
It happened on a **single device with no other client**, for both new and existing notes,
and it stopped when "Sync on file change" was turned off.

The cause was that **the plugin was conflicting with itself**. `syncSingleFile` proceeds in the order
"stat -> PROPFIND -> classify -> upload -> record base", but **there is a gap between the upload landing and the
base being recorded**, and if the next cycle does a PROPFIND in that gap it observes "remote new, base old".
It read that as "the remote changed", and since typing was continuing and `localChanged` was also true it
judged **both changed = conflict** and wrote the 3-way merge result back into the file being edited. The reported `HTTP 423 (PUT)` was
the same overlap seen from the server side (colliding PUTs to the same file).

> **A refuted hypothesis is recorded here.** At first the conclusion was "on servers that return no checksum, `remoteId` permanently mismatches", and the absence of `checksums` in the reporter's capabilities seemed to support it. However, measuring with the
> official Docker image (`nextcloud:latest` 34.0.3) showed that **even when capabilities has no `checksums`, PROPFIND returns `oc:checksums` and it matches the local SHA256**. Had the fix based on this hypothesis
> (record the etag when the capability is false) been implemented, it **would have newly created the same bug for every user of the official image**.

**Serialisation (`WOV-1`)**

- **A per-path `AsyncMutex`** (reusing `src/util/AsyncMutex.ts`; no new exclusion mechanism is written)
  wraps `syncSingleFile` / `deleteSingleFile` / `renameSingleFile`. The critical section is
  **the whole span "from PROPFIND to recording base"** (if split, the gap would reappear elsewhere).
- **It is not a global lock.** Syncing is dominated by network waits, and a single lock would
  line all files up in one queue. The tests pin **both directions** (the same path waits / different paths stay parallel).
- `renameSingleFile` acquires **both the old path and the new path** in **lexicographic order** (so that crossing `a->b` and `b->a`
  cannot deadlock).
- The early returns from `isSystemExcluded` / `isSyncRunning` are **outside the lock** (a decision to do nothing must not be queued behind real work).
- **Entries are not discarded.** `AsyncMutex` has no API to ask the queue length, so a safe discard condition cannot be written.
  Silently losing the exclusion is worse than the memory of one Promise per path.

**Protecting the file being edited (`WOV-2`)**

- **A remote -> local write** (download / conflict resolution) is **deferred while the target path
  was modified within the edit window**, and is put on the `retryQueue` to be re-evaluated next time.
- **Uploads are not deferred.** They only read the file and cannot collide, and deferring them
  would remove the reason "Sync on file change" exists.
- **The whole decision is deferred (not only the write).** The write is the last step of a series that includes recording base,
  and skipping only the write would make the state DB claim content the real file does not have (the price paid for the untracked-both-sides rule of §5.3).
  Therefore the guard is placed at a single point, the four-quadrant branch (`processRemoteFile`), and not scattered over the 7 write sites.
- The "being edited" decision uses **the last edit time per path** (`lastLocalEdit` in `main.ts`, self-pruned on read).
  The debounce pending set cannot be used because it is **cleared at the moment of firing** (it is always empty when the sync starts,
  so at the only moment it is asked it always answers "not being edited").
- The window is **the same constant** as the debounce window (`EDIT_WINDOW_MS`). If it were shorter, the gap that was added to close it
  would open again.

Tests: `WOV-1` (`watchOverlap.test.ts`) / `WOV-2` (`writeWhileEditing.test.ts`). Both
**verify both the under-detection and over-detection directions by mutation**.

### §5.7c Watch and Wi-Fi only on mobile (`MWM-1` to `MWM-6`)

- Watch runs according to the value of `watchOnChangeEnabled` regardless of the platform. The runtime platform guard (the former `G7-2` `isWatchModeActive`) was removed. The origin of the value (switched ON on this device, or a copied setting) is not distinguished.
- Rationale: watch reacts at the moment of editing, and at that moment the app is always in the foreground. Changes lost to an interruption are detected as differences by the next full sync (startup, resume, or manual).
- The initial mobile default remains OFF (opt-in; §15).
- The 6 operations (`syncSingleFile` / `deleteSingleFile` / `renameSingleFile` / `createSingleFolder` / `deleteSingleFolder` / `renameSingleFolder`) evaluate, at their entry, the same Wi-Fi only decision as a full sync (`SyncEngine.isBlockedByWifiOnly` -> `isCellularBlocked`, port `WatchDeps.isBlockedByWifiOnly`). While blocked on cellular, they touch none of the lock, StateDB, network, pending queue or notification, and leave only one log line `watch: skipped <op> <target> — Wi-Fi only is on and the connection is cellular`.
- A skipped change is put on neither the retry queue nor the pending set. The scan of the next full sync picks it up (a rename converges as deletion of the old path plus upload of the new path, and is not propagated as a MOVE).
- The Wi-Fi only decision itself is unchanged (it stops only when the connection is known to be cellular; it does not stop when undeterminable, on iOS, or on desktop).
- The settings-screen description does not branch by platform.
- Tests: `MWM-1` (`settingDefinitions.test.ts`) / `MWM-2` (`watchWifiOnlyGate.test.ts`) / `MWM-3` (b-1 `mobileWatchWifiOnly.b1.test.ts`) / `MWM-4` (b-3 `mobileWatch.b3.test.ts`) / `MWM-5` (`watchWifiOnlyWiring.test.ts`) / `MWM-6` (`mobileFirstRunDefaults.test.ts`).

### §5.8 Sync on foreground resume (`RSY-1` to `RSY-4`, `RMO-1`, GitHub discussion #44, issue #49)

**When the app returns to the foreground, one run of the existing incremental sync is started. It is common to all platforms and
has no branching on `Platform.isMobile`.**

**Background**

On mobile, periodic sync (§5.4) is disabled, and watch mode (§5.7c) is OFF by default and works only while the app is in the foreground, so if Obsidian is left in the background
there is **no trigger to sync at all**. Changes from another device are not reflected until a manual sync or an app restart.
Foreground resume is **the only moment at which it is certain that the app is alive and the user is looking at it**, and it is a trigger that does not depend on the reliability of background execution.

**Specification**

| Item | Content |
|---|---|
| Trigger | `visibilitychange` on `document` (`visibilityState === 'visible'`) and `focus` on `window`. `onAppResume` in `src/util/appResume.ts` |
| What it starts | **The existing `syncManual()`**. No resume-specific sync process is added |
| Cooldown | **5 minutes** (`RESUME_SYNC_COOLDOWN_MS`). **Not a user setting** |
| Cooldown reference | `stateDB.getLastSyncTime()` = **the common time that every sync updates in its `finally`** (`SyncEngine.ts`) |
| Target platforms | **All platforms**. Desktop has the same hole because timers stop during sleep |
| When the sync engine is uninitialised | **Do nothing. No error, no notification** (the user has not requested a sync) |
| Suppression condition (`RMO-1`, issue #49) | **When `startupSyncDelaySeconds === 0`, resuming does not sync.** The check comes before the cooldown and reads the current value on every call (a setting change is reflected from the next resume immediately, with no reload) |

**Design points**

- **By using the common `lastSyncTime` as the cooldown reference, double firing with the startup sync is prevented without any special case.**
  Startup -> startup sync -> an immediate `visibilitychange` falls within the cooldown and does not run. **No dedicated flag,
  timer or record of the startup time is kept.**
- **Multiple-start prevention is not placed on the caller side.** The `running` guard at the top of `syncManual` simply takes effect.
- **Subscribing to `window.focus` as well is intentional.** It shares the same subscription as the Login Flow fix for issue #34 (verified on a real device by `loginFlowResume.b3.test.ts`),
  and the behaviour is not changed without reason. The cooldown absorbs the increased firing frequency on desktop.
- **`lastSyncTime` advances even when a sync fails** (because `setLastSyncTime` is in the `finally`). Therefore a retry does not run when the app is switched away and back right after a failure.
  This is an **intentional choice leaning toward preventing a retry storm**; the resume trigger is
  "insurance that picks up what was missed", not "a mechanism that retries failures".
- The protections of §5.7b (deferring write-back to a file being edited, per-path serialisation) are inside `syncManual`, so
  **they take effect automatically on this path too**.
- **The startup sync and the resume sync are firings, at different moments, of the same question: "should we sync because the app has become available?"**
  `startupSyncDelaySeconds = 0` is already a declaration "do not sync merely because the app appeared", and
  the same answer applies to the resume sync. **No dedicated toggle is added** — it is derived from the one existing setting.
  Version 1.0.2 implemented the resume sync independently of every setting, which took away the state reachable up to 1.0.1,
  "turn off periodic sync, startup sync and watch to get fully manual operation" (the regression reported in issue #49).

Tests: `RSY-1` to `RSY-4` (`appResume.test.ts` / `resumeSyncHandler.test.ts` / b-3 real device) and `RMO-1`.
`RSY-2` **includes a clause that pins the exported default cooldown value itself** — because mutation verification
found a hole: "the test passed its own value, so setting the shipped constant to 0 left everything green".

### §5.9 Single definition of the remote identifier (`PWR-1` to `PWR-3`)

**There is exactly one definition of "what is the remote side of this file".** The value recorded after an upload and the value
read by the next classification both come from the same `remoteIdOf()`.

```
remoteIdOf(remote) = sha256 if a checksum exists / otherwise etag / otherwise size
```

**Background (a reproduced failure)**

The recording side (`TransferService`) **unconditionally wrote SHA-256**. Its rationale was Nextcloud's behaviour
(if `OC-Checksum` is sent the server stores it and returns it via `oc:checksums`), and **plain WebDAV was not considered**.
`StandardWebDAVClient` returns a hard-coded `checksum: null`, so the classification side reads the ETag.
**A hash and an ETag never match.**

Reproduced in layer a (`plainWebdavRemoteId.test.ts`):

| After the upload, the local file is | Measured |
|---|---|
| Unchanged | One unnecessary download (the download path then records the real remote value and it converges) |
| Changed | **Both changed = conflict.** The merge result is written back into the file being edited |

**In the cycle "upload -> edit -> sync" the next edit arrives before convergence, so it becomes a conflict every time.**

**Specification**

| Item | Content |
|---|---|
| Formula | **Only** `remoteIdOf()` in `src/sync/remoteIdentity.ts`. The 3 classification sites use the same one |
| Nextcloud (a client that returns a checksum) | After the upload, record `localHash` / `sha256`. **No extra round trip** |
| Plain WebDAV (a client that does not return one) | After the upload, do `statFile` and record `remoteIdOf(fresh)`. **+1 PROPFIND** |
| Discriminator | `NextcloudFeatures.isNextcloud` (**which client was chosen**) |
| When the re-read fails | **Record `localHash` as before** (if nothing were recorded, base would stay stale and induce both changed = conflict next time) |

**Design points**

- **`hasChecksums` (the server's capability claim) is not used.** It was measured, in the refuted-hypothesis case of §5.7b, that even when the capability is false
  PROPFIND returns a checksum. Using it as the discriminator would build the same bug for users of the official Docker image.
  This clause looks at **a property of the client implementation**, not at the server's claim.
- **It is not discriminated by per-file `remote.checksum !== null`.** For the upload of a new file a synthetic remote with
  `checksum: null` is passed (`SyncEngine.ts`), so an extra PROPFIND would run for every new file on Nextcloud.
- As a by-product of the unification, the **inconsistency of recording `idType` as `'etag'` on the size fallback** (1 of the 3
  sites) was fixed.

Tests: `PWR-1` to `PWR-3` (layer a) plus **b-4 (real Apache mod_dav) confirms the premise** — it verifies that the real server returns
`checksum: null`, and that the ETag is stable when unchanged and changes when the body changes.
## §6. Conflict resolution

> **Implementation details** (`handleConflict` kind classification, strategy dispatch, MergeEngine, action execution) are in docs/plan.md §8.

### §6.0 Two-level conflict resolution
Conflict resolution has **two levels**. (1) The **primary strategy** tries to resolve the conflict. (2) Only the **parts** that the primary strategy `merge` could not truly auto-resolve are settled by the dedicated **`conflictStrategy`**.
- **Primary strategy assignment**: markdown is always special-cased (independent of `autoMergeFileTypes`): **frontmatter = `frontmatterStrategy` / body = `autoMergeFileStrategy`**. A non-md file whose extension is in `autoMergeFileTypes` is resolved **as a whole by `autoMergeFileStrategy`**. Every other file is resolved **as a whole by `otherFileStrategy`**. The default of `autoMergeFileTypes` **excludes md** (md is special-cased; md is also removed automatically from existing lists by `migrateMarkdownAutoMergeType`).
- **`conflictStrategy`** (values: `conflict-markers` (default) / `latest-mtime` / `local-win` / `remote-win` / `biggest-size`) settles diff3 conflict regions in the body and scalar clashes in the frontmatter **part by part**. `conflict-markers` writes both versions as markers into the body (conflicted). **The frontmatter cannot hold markers inside `---`, so it uses a deterministic `latest-mtime` fallback.** A binary body is either safe-held (markers) or resolved by adopting one side (deterministic value). Deterministic primary strategies other than `merge` never conflict, so `conflictStrategy` does not fire for them. With the default `conflict-markers` the result is identical to 0.7.24-beta.1 (no regression). Tests: `conflictStrategyLevel2.test.ts`, `CF-14`.

### §6.1 Strategy per file type
A conflict (both sides changed) is **always settled** by "file type -> the single `SyncStrategy` of that type". The user sees **4 settings** (SC-001; the frontmatter-specific one is the fourth):
- `autoMergeFileTypes` (**Auto Merge File Type**; continues the role of the former `mergeableExtensions`. Default `['txt','cpp','py','c','h','hpp','rs','go','ts','js','java','sh']` (`md` is not included; markdown does not depend on this list and is always special-cased). Comma-separated input; on save it is lower-cased, leading dots are stripped and duplicates are removed = `parseMergeableExtensions`). **A file whose extension is in this list is an Auto Merge File; everything else (including files without an extension) is an Other File. An empty list means everything is an Other File** (CSF-1).
- `autoMergeFileStrategy` (the **body** strategy of an Auto Merge File. Default `merge`. All 5 values allowed).
- `otherFileStrategy` (the **body** strategy of an Other File. Default `latest-mtime`. 4 values, excluding `merge`).
- `frontmatterStrategy` (the strategy that resolves the frontmatter block of a `.md` file independently of the body. Default `merge`. All 5 values allowed. It replaced and absorbed the former experimental `frontmatterScalarConflictPolicy`, so the number of visible settings did not grow).

**Independent frontmatter/body resolution**: for every `.md` file that has frontmatter, a conflict resolves the frontmatter block with `frontmatterStrategy` and the body with the type strategy (`autoMergeFileStrategy` / `otherFileStrategy`) **independently, then recombines them** (`ConflictResolver.decideMarkdown`). Even when md is outside the Auto Merge File Type list, the frontmatter is resolved independently (decided by `isMarkdown`). Frontmatter resolution never writes markers, so a frontmatter-only difference never makes the file conflicted; markers enter the body only when the body is `merge` and a same-line conflict occurs. A `.md` file without frontmatter and non-md files use the previous whole-file path (zero regression). Test: the frontmatter-strategy tests in `tests/a-no-nextcloud/merge/frontmatterStrategy.test.ts`.

`SyncStrategy` = `merge | biggest-size | latest-mtime | local-win | remote-win` (`src/types.ts`). Classification is `ConflictResolver.strategyFor`; file-type decisions are `isAutoMergeFile` / `isMarkdown`. Tests: `CSF-1`, `CSF-10` (default).

### §6.2 Strategy dispatch (single path `ConflictResolver.decide` + `SyncEngine.handleConflict`)
After classification, the `SyncStrategy` of the type is applied. Size and mtime are evaluated from the local `stat` (size/mtime) held by SyncEngine and from `RemoteFileInfo` (size/lastModified) (no new network fetch); ConflictResolver is a pure decision (no I/O).
- **`merge`**: **a base-aware true 3-way merge** (the base is the last-synced body held by `MergeBaseStore` (`merge-base-<deviceId>.json`)). **When the base is non-empty, `node-diff3` is the main engine** (non-overlapping edits merge cleanly; only true same-line conflicts get single-layer markers = lower marker frequency). **Only when the base is empty, it falls back to `reconcile-text`** (migration; `node-diff3` is added to count regions). The base is recorded for Auto Merge File Types **and for all `.md` files** (FR-015; `isAutoMergeFileType(path)||isMarkdown(path)` is used identically for reads and writes, so deletions in the frontmatter propagate even when md is not an Auto Merge target). Tests `MB-1` to `MB-14`, `MM-8` to `MM-10`.
  - **Non-text (binary)**: cannot be merged -> **both sides unchanged plus `isConflicted:true`, a safe hold that writes no markers** (FR-005a, zero corruption; the `safe-hold` action. Not an error, no retry). Binary detection looks for NUL / U+FFFD in the content (`isLikelyBinary`). Test `CSF-4`.
  - **Marker re-entry guard (the core of data safety)**: before merging, detect whether local/remote contain **a complete set of this plugin's conflict markers** (**both** the opening `^<<<<<<< LOCAL` **and** the closing `^>>>>>>> REMOTE` are present; `hasCompleteMarkerSet`). If so, **do not auto-merge; `safe-hold`** (existing markers are not wrapped in new markers = depth does not grow, no push). A bare `<<<<<<< HEAD` and the like does not fire by mistake (FR-039-4). When the user removes the markers, normal merging resumes (self-healing). Without this guard, a marker-laden body is wrapped recursively on every re-merge and grows geometrically (real damage: 5KB -> 62KB, 3-fold nesting, 12 duplicates). Tests `MM-1` to `MM-5`, `MM-11` (b1).
  - **Orphan-marker self-heal (FR-001 to FR-006)**: an orphan marker with **only one of the opening/closing** markers (for example the trailing `>>>>>>> REMOTE` line was left behind by a past manual resolution; `hasOrphanMarker` = XOR) is **not treated as re-entry and goes through the normal 3-way merge**. The old implementation (`REENTRANT_MARKER_RE` matched a single marker) fell into a permanent `safe-hold` (no push) on an orphan marker; the remote orphan marker never disappeared and **was re-counted as conflicted on every sync, a deadlock** (it happened with real data on a real server). Narrowing the check to the complete set makes an orphan marker merge, converge and be pushed, removing the remote orphan marker as well and self-healing (converges in finite steps; SC-001/002). When an orphan is detected, `SyncEngine.handleConflict` emits a debug log (FR-004). Nesting (two or more complete sets) keeps `safe-hold` via `MergeResult.hold` as before (SC-003, zero regression). Tests `OM-1` to `OM-4`.
  - **Clean**: adopt the merge result (`merged`). Test `CSF-2`.
  - **Text conflict (body)**: write full-file conflict markers and set `isConflicted:true` (FR-005). Test `CSF-3`.
  - **Frontmatter conflict (semantic merge, hardened)**: the frontmatter is resolved **only structurally (as data)** and **conflict markers are never written inside the `---` block** (SC-001/002). The implementation is a full hardening of the earlier semantic merge.
    - **split**: the body/frontmatter split uses Obsidian's official `getFrontMatterInfo` (the home-grown regex was removed). A `---` separator inside the body is not mistaken for a frontmatter fence, and CRLF and trailing-space fences are tolerated (HFM-8, FR-003).
    - **parse/serialize**: parse and re-serialize with `parseYaml` / `stringifyYaml` (Obsidian's official functions). **Production does not import raw `js-yaml`** (read consistency identical to the host. HFM-1, FR-004).
    - **Array fields** (tags/aliases/related and so on, where the value is a list): **a base-relative true 3-way SET merge** (HFM-2, FR-006). Presence/absence of each item is binary, so a local/remote mismatch is decided definitively for "the side that differs from base" = **deletions propagate** (one side deleted and the other still at base -> deleted; both deleted -> absent; additions on both sides are kept). In a real bug (a server-side program rewrote tags from `[1,2,3]` to `[2,3,4]`), the deletion of `1` propagates and the result is not the union `[1,2,3,4]`. **When no base exists, it degrades to a de-duplicated union** (deletions are undetectable but additions are never lost. HFM-3, FR-007). Items are normalized with `parseFrontMatterStringArray` before the set operation, so near-duplicates that differ by `#tag`/`tag` or whitespace converge to one entry (HFM-4, FR-008). The output order is stable and deterministic: base order -> addition order (independent of mtime. HFM-5).
    - **Scalar fields**: 3-way resolution. When both sides changed to different values, the **fixed `latest-mtime` tiebreak** applies (remote wins ties; the former `frontmatterScalarConflictPolicy` was removed and fixed. HFM-6). **delete-vs-modify** (one side deleted the key, the other edited it) is also judged against base and settled by `latest-mtime` (FR-005). A nested YAML object is treated as an opaque scalar (adopted whole, no partial merge; option A continues).
    - **Unparseable side**: if either side cannot be parsed as a YAML mapping, `FrontmatterMergeStrategy.merge` returns `success:false` (HFM-7, FR-005), and `MergeEngine` **adopts one side's whole frontmatter block** (following the scalar policy: `latest-mtime` takes the newer side / `remote-win` / `local-win`. HFM-10). **The frontmatter is never text-diffed**, so diff3 markers never enter `---` (HFM-9). **The diff3 fallback applies to the body only.**
    - **backstop**: if the merge result contains stacked markers, it is `hold` -> `safe-hold` as before (HFM-11, shared with item (3) of the circuit breaker below). Together with HFM-9, nested markers cannot arise from the frontmatter path. Convergence (re-sync keeps the frontmatter idempotent; markers do not multiply; arrays do not multiply) is HFM-13 (FR-011). **The frontmatter resolution strategy itself (merge / whole-side) is chosen by `frontmatterStrategy`** (anything other than `merge` adopts the whole frontmatter block from one side). Tests `CSF-3`, `HFM-1` to `HFM-14` (`tests/a-no-nextcloud/merge/`, `support/obsidianDouble.test.ts`).
  - **Circuit breakers**: (1) merged length < max(local,remote) x 0.5 (detects content loss). (2) **Inflation guard (FR-005b)** — when a clean candidate is longer than "the sum of both input body lengths" or "contains a run of 2 or more duplicated consecutive lines", it is regarded as a reconcile duplication bug and demoted to a conflict (only on the clean path with `hadConflicts:false`. Length-based checks do not apply to the marker path, where exceeding max is normal for legitimate single-layer markers). (3) **Nested-marker backstop (FR-039-5)** — if the merge result contains **stacked plugin markers** (`<<<<<<< LOCAL` appears again before being closed by the matching `>>>>>>> REMOTE`; `hasNestedConflictMarkers`), set `MergeResult.hold`, **demote to `safe-hold`** and do not push (a backstop for paths that slip past the re-entry guard; independent of length, no false positives). Tests `CSF-5` (SC-009), `MM-6`/`MM-7`.
- **`biggest-size`**: adopt the side with more bytes (`prefer-local` / `prefer-remote`). Test `CSF-6`.
- **`latest-mtime`**: adopt the side with the newer mtime. **Note that clock skew between devices can let an old edit silently overwrite a newer edit** (FR-012; stated in the tooltip). Test `CSF-7`.
- **`local-win` / `remote-win`**: deterministically adopt the named side. Test `CSF-8`.
- **tie (`biggest-size` with equal size / `latest-mtime` with equal mtime)**: **both sides unchanged; a no-op success that is neither an error nor conflicted** (FR-009; the `no-op` action. StateDB unchanged -> re-evaluated next sync = self-healing). **However, a tie leaves both sides divergent, so the root-ETag short circuit is invalidated (`setRemoteRootEtag(null)`) to force a real scan next time** (otherwise the short circuit rebuilds from the stale State and silently uploads local = data loss. See the §8a.5 tie special case / ES-11). Test `CSF-9`.

### §6.3 No hold strategy; always settled (FR-010)
There is **no** user-selectable "Error/hold" strategy. A conflict is settled by one of `write` (merged/markers) / `prefer-local` / `prefer-remote` / `safe-hold` (non-text) / `no-op` (tie). The overwritten losing side can be restored from the Nextcloud version history (when the remote loses). **The former dedicated newest-wins branch for config-folder JSON (`.obsidian/*.json`) was removed**: the extension `json` is outside the Auto Merge File Type list, so it is an Other File with `latest-mtime` (default) and naturally resolves to the equivalent of newest-wins (no markers are written, so JSON stays safe. FR-013, CSF-12). A file held by `safe-hold` or markers leaves StateDB unchanged, is detected again next time, and converges through a strategy change, Compare with remote (Push/Pull), or a change on one side (self-healing). Tests: `CSF-1` to `CSF-13`, `SyncEngine.handleConflict — strategy actions` (`tests/a-no-nextcloud/sync/syncEngine.test.ts`).

> **Migration of old settings (R3)**: `loadSettings` maps the 3 old settings onto the new model and removes the old keys automatically with `pruneObsoleteSettings` (self-healing). `mergeableExtensions` -> `autoMergeFileTypes` / `autoMergeEnabled=true` -> `merge` / `autoMergeEnabled=false` + `conflictFailurePolicy` (`local-wins` -> `local-win` / `remote-wins` -> `remote-win` / `conflict-markers`, `error` -> `merge`) / `otherFileStrategy` <- `conflictFailurePolicy` (same mapping; `conflict-markers`, `error` -> `latest-mtime`) / `frontmatterConflictStrategy` -> discarded. New users get `DEFAULT_SETTINGS`. The old `frontmatterScalarConflictPolicy` migrates to `frontmatterStrategy='merge'` regardless of its value (mapping it to the same-named whole-side value is not adopted because it would regress by taking away the array union), and the old key is pruned. Tests `CSF-11`, `FR-010`/`FR-011` (`tests/a-no-nextcloud/sync/settingsMigration.test.ts`).

> **retryQueue**: file paths that failed through an `error` policy skip, `NetworkError`, `FileLockedError` and the like are put on the in-session `retryQueue` (`SyncEngine`) and **retried right after the initial sync completes and on the next sync**. The purpose is to recover transient failures (network loss, locks), not to retry permanent failures forever. It is not persisted (in-process only). `processFileWithRetry` **re-queues only `NetworkError`**; local I/O errors (ENOENT and so on) are only recorded and not retried (retrying would fail again). Test: `RT-1` (`tests/a-no-nextcloud/sync/retryQueue.test.ts`).

> **Injectable retry predicate in withRetry()**: the exponential-backoff utility `withRetry(fn, maxRetries, initialDelayMs, shouldRetry?)` in `src/util/retry.ts` retries only `NetworkError` instances as before when the fourth argument `shouldRetry` is omitted (**existing behaviour is fully preserved**). A caller can inject any predicate, and the WebDAV request-level read retries of §5.6a are implemented through this mechanism. It is a separate layer from the retryQueue (§6.3 above): it retries **immediately within the same sync pass**, whereas the retryQueue carries a file-processing failure over to the next sync (a cross-sync mechanism). Test: `RT-2` (`tests/a-no-nextcloud/util/retry.test.ts`).

### §6.4 Conflict list and clearing, per-file/bulk force-resolution, clean-side snapshot restore
Unified list display, open-to-inspect, mark resolved (clear the flag plus update the base), automatic clear when local==remote, and re-detection prevention. This includes the fix for the bug "3 conflicts never go away". Each conflicted file in the Sync status dialog can be settled immediately with 4 choices (Use remote / Use local / Latest modified / Biggest size) (bulk resolution is also available); the default label and the choices are fixed.

**Clean-side snapshot restore (data safety)**: the path where a `merge`-strategy text conflict writes markers (`clean:false` in `resolveByWrite`) writes the marker content locally and uploads it to the server, **overwriting and losing both clean versions (local pre-merge / remote)**. A force-resolution that pulled/pushed the current state (with markers) therefore could not restore a clean version, and it also set `isConflicted:false`, so "only the warning disappeared while the content stayed full of markers". The countermeasure: **at conflict detection (just before the markers are written), both clean versions are saved to `CleanSideStore`** (`conflict-clean-<deviceId>.json`, persisted per device, a mirror of MergeBaseStore) (CSS-1/12). If a snapshot exists, force-resolution **restores from it** (Use remote -> clean remote / Use local -> clean local is written to both sides and converges; Latest/Biggest dispatch on the saved metrics) (CSS-2/3/4); if none exists, it falls back to the previous pull/push (CSS-5). A snapshot is discarded on convergence, resolution or deletion, and the sweep at the end of a sync clears every "path that is not conflicted" (no leak; bounded by the conflicted count. CSS-6/8). Only the **marker-writing path** is covered: safe-hold (non-text) and a download-size hold push nothing and leave both sides clean, so the previous path restores them correctly and no snapshot is taken (CSS-12). No new user setting is added (CSS-7). ### §6.5a Making server-side locks (423) visible (GitHub issue #58)

**Problem**: `fileLockingEnabled` defaults to `false` (lost-update safety rests only on the If-Match precondition of §6.5 above; no LOCK/UNLOCK round trips are used). As a result there was no path anywhere that detected a server-side lock held by another client (typically a leaked lock with `Timeout: Infinite` left by the Nextcloud Text web editor). Whether in the four force-resolution choices (§6.4) or in an ordinary sync push, a `423` returned for PUT/DELETE showed only an unexplained bare `HTTP 423 (PUT)` message, and the conflict never resolved.

**Response**: in `uploadFile` (PUT) and `deleteFile` (DELETE) of `NextcloudClient`/`StandardWebDAVClient`, only when the response is 423, one additional Depth:0 `lockdiscovery` PROPFIND is issued. The pure function `readLockDiscoveryOwner` in `src/network/dav/propfind.ts` reads the lock owner from `D:lockdiscovery > D:activelock > D:owner` (the RFC 4918 standard, preferred) or `nc:lock-owner` (a Nextcloud extension, namespace `http://nextcloud.org/ns`). If an owner is obtained, it throws `ServerLockedError` (`src/types.ts`; it extends `NetworkError` and follows the same pattern as `RemoteRootMissingError`/`RemoteListingUnreadableError` of overwriting `this.message` after `super()`); if not, or if the PROPFIND itself fails, it falls back to the plain `NetworkError(423, ...)` as before. Because `ServerLockedError` extends `NetworkError`, the existing `instanceof NetworkError` branches (retry queue, `SyncErrorDetail` recording, `Notice` creation during force-resolution) need no change at all — they benefit just from the more detailed message.

**"Excluded from sync (skipped)" is not a new mechanism**: the `retryQueue` of `SyncEngine` is designed to be drained only at the start of the next `sync()` call, so a `NetworkError` including 423 already had the self-healing property of "do not retry within the same cycle; retry in the next cycle". All this change did was make the message more detailed.

**Out of scope (intentional)**: releasing a server lock from inside the plugin (sending UNLOCK) is not provided. While the origin of the lock (another client / a Text editor session) cannot be determined, a forced release risks overwriting another person's in-progress edit. Release is left to asking the server administrator, or to closing the session that holds the lock (for example the Text editor tab) (documented in the README FAQ).

**Facts found by real-server verification (`SL-2`, discovered by a b-1 run before a stable release)**: the presence of an owner depends on the server and on where the lock came from, and is not always guaranteed. On the Nextcloud of this project's Docker test suite (`tests/docker/run.sh`), for a lock acquired by the plugin's own `lockFile` (`X-User-Lock: '1'`), `lockdiscovery` returned 207 without an owner (in the environment of the reporter of issue #58, the owner did appear for a Nextcloud Text editor lock). Given this, `SL-2` claims only "if an owner is obtained it is read correctly" and does not claim "an owner is always obtained". The fallback is not an exception path but a routine path, and even when no owner appears it is no worse than the existing behaviour (the bare `HTTP 423 (PUT)`).

Tests: `LDO-1` to `LDO-4` (a; `readLockDiscoveryOwner` unit, `tests/a-no-nextcloud/network/dav/propfind.test.ts`), `SLE-1` to `SLE-12` (a; wiring of `uploadFile`/`deleteFile` in `NextcloudClient`/`StandardWebDAVClient`, `nextcloudClient.serverLock423.test.ts` / `standardWebDavClient.serverLock423.test.ts`), `SL-1` to `SL-2` (b-1; `serverLocked423.b1.test.ts`. `SL-1` is the end-to-end reproduction of 423; a single-account test harness cannot reproduce another person's lock, so it is a waiver (same F3 reason as `LK-4`/`LK-5`). `SL-2` verifies the shape of the lockdiscovery response against a real server; when no owner is present it only logs a warning and does not fail).

## §8. Deletion safety

- **A remote deletion applied locally respects Obsidian's "Deleted files" setting** (OS trash / vault `.trash` / permanent deletion). It covers normal notes, folders and files not tracked by Obsidian. A nonexistent file is idempotent. Errors are reported and the sync continues.
- **Propagating a local deletion to the remote requires proof, whatever the path (GitHub issue #46)**: a file that is "tracked, absent locally, and not a rename" has the server's actual entry checked before DELETE, **whether or not it appears in the remote listing**. DELETE only on a match; if Remote Modified, cancel the deletion, download the latest and notify; if the checksum cannot be confirmed, keep the file (no proof = no deletion).
  - **When it appears in the listing**: compare the checksum held by the listing (or `recalcChecksum` if none) with the base (`applyLocalDeletion`).
  - **When it does not appear in the listing**: take existence and checksum together with one `statFile` (Depth:0 PROPFIND); on a 404, **issue no DELETE** and drop the tracking (state / merge base / clean-side snapshot); if it exists, route to the same `applyLocalDeletion` as above. If it cannot be determined (a network error and the like), keep the tracking and retry next time (`G1-2`). Full sync, incremental sync and watch mode all go through the same `DeletionService.deleteLocallyMissing`.
  - **The error of the old specification (re-introduction is forbidden)**: this clause used to say only "re-confirm the Base match with a PROPFIND before deletion", but the implementation **proved the state only when the file appeared in the listing**. For a file not in the listing it issued a bare `deleteFile` and treated 404 as success (on the premise "not in the listing = not on the server either"). Issue #46 showed that the listing can in fact be incomplete, which broke that premise. The earlier statement "fact 5: file deletion has a proof guard" was likewise **true only when the file appeared in the listing**, for the same reason.
  - At most one round trip per candidate. In the normal case where the listing is complete, the previous single DELETE is simply replaced by a single PROPFIND, with a net increase of zero. In incremental sync, unchanged remote files always fall on the "not in the listing" side, so each local deletion costs one extra PROPFIND (accepted; leaving a DELETE without proof costs more).
  - Plain WebDAV returns no checksum, so "exists but cannot be proven" falls to keep. This is the same as the existing behaviour for files that appear in the listing, and is not a new constraint.
  - Tests: `GDP-14` to `GDP-19` (a; combination table for `DeletionService` alone), `GDP-20` to `GDP-25` (a; engine integration), `GDP-29` (round trips), `GDP-32` (b-1).
- Mass-deletion circuit breaker: if the local deletion candidates in one sync exceed **max(20, tracked file count x 0.2)**, the bulk local deletion is aborted (a defence against a remote listing that makes most tracked files look gone = server failure or erroneous sync). The threshold is centralized in the pure helper `massDeleteLimit` (`src/util/limits.ts`; not a setting). Test: `DEL-3` (layer a, `tests/a-no-nextcloud/sync/massDeletion.test.ts`). The b-1 full-scan e2e (`deletionSafety.b1.test.ts`) is deferred (`it.skip`, SF-1 waiver) pending a SyncEngine harness.
- **Absence deletion works even when the remote listing is empty (GitHub issue #50)**. The full-scan path that deletes "tracked, present locally, absent from the remote listing" runs candidate enumeration -> mass-deletion breaker -> per-candidate Depth:0 PROPFIND 404 re-confirmation -> local trash, **regardless of the listing count**. The defence is **only these 2 stages (breaker + 404 re-confirmation)**; there is no implicit guard of "skip everything when the listing is empty".
  - **History of the old guard (re-introduction is forbidden)**: the `remotePathSet.size > 0` guard was introduced in `3d74a01` (0.2.1-beta.7) as "prevention of mass erroneous deletion by an empty/failed listing", but the very next change `c441390` (0.2.1-beta.8) added the breaker and the 404 re-confirmation and **fully subsumed it**. From then on it only produced false negatives: on a small vault whose tracked files had all vanished from the server (typically a 1-file vault deleted from another device) it recognised `remote=0` yet ended with `del=0`, and because the root-ETag short circuit rebuilds the listing from State next time, it also **did not self-heal** (the symptom of issue #50).
  - **Why an empty listing can be trusted**: the listing PROPFIND throws on anything other than 207, and a root 404 is distinguished as `RemoteRootMissingError` (§5.2). **It also throws when the body of a 207 itself cannot be read** (`RemoteListingUnreadableError`, GitHub issue #51). Previously the body of a 207 was trusted unconditionally, and a truncated XML, a body that is not XML (such as a proxy error page), and a document that is not a `multistatus` were all indistinguishable from "an empty listing with 0 entries". That confused **the server's claim** "the listing is empty" with **a retrieval failure** "the answer could not be read"; on a large vault (many files) it showed up as a false firing of the breaker, and on a small vault it ended, in versions before this fix, with the whole folder being trashed (a strong suspect for the cause of issue #46). **The confusion "retrieval failure = empty array" does not occur as long as it is closed by the validation above** (it did occur before it was closed). A truly empty listing (a legitimate 207 multistatus with 0 responses) passes this validation and flows into absence deletion as before. A false empty listing (a server-side listing anomaly where content is partially missing but the body is readable) is rejected because the per-candidate 404 re-confirmation returns 200, and the breaker stops it if it is large. Tests: `EAD-1` to `EAD-4` (a), `EAD-B1-1` (b-1), `ULG-1` to `ULG-18` (a).
- **A missing vault folder means "re-seed", not "deletion" (FR-007 to FR-013)**. When `getFiles('')` returns `RemoteRootMissingError` for a tracked vault, nothing has been proven about any individual file (the absence of the whole folder can also occur through a server-side misconfiguration, a rename, or a migration in progress). And because the remote path of the vault folder is **decided automatically by the plugin from the vault name**, the user cannot recreate it. Therefore local is treated as authoritative and restored in this order:
  1. `createVaultRoot()` (the parent is best-effort MKCOL; **only the vault folder itself is judged strictly**)
  2. Only when **MKCOL 201 = proof that it really did not exist** is obtained: `StateDB.reset()` -> upload all local files and MKCOL all local folders (including empty ones) through the initial-sync path. **Nothing is deleted locally.**
  3. **MKCOL 405 (it actually exists) = the 404 of the listing was wrong.** In this case neither a tracking reset nor a deletion is done; it is recorded as an error and the next sync rescans for real. Any other MKCOL failure (403/5xx/network) likewise performs zero destructive operations.
  - The initial sync (empty State) continues as an empty listing as before and does not enter this path. Tests: `VRR-1` to `VRR-7` (a), `VRR-B1-1` (b-1).
- `app.vault.adapter.remove()` is forbidden except for deleting temporary files. Idempotent deletion (404 treated as success) test: `DEL-2`.
- **Visibility of skipped paths + report notes + directory-side bulk resolution**: when a mass-deletion circuit breaker fires on either side — the directory side (this section, `massDeleteLimit`) or the file side (`DEL-3`) — the deletion-candidate paths actually skipped are recorded **in full, with no cap**, in the session's error detail (`SyncErrorDetail`). The directory side keeps them in `dirBreakerSkipped` (`{ deleteRemote: string[]; trashLocal: string[] }`, by category) and the file side in `skippedPaths` (`{ all: string[] }`) (one error never holds both).
  - **Display is unified into a report note, not inline in the modal** (the capped inline display in the modal, `formatSkippedPathsForDisplay`/`MAX_SKIPPED_PATHS_SAMPLE`, was abolished). Clicking the relevant error row under "Errors in last sync" in the Sync status dialog writes and opens a fixed-name report note that is overwritten each time (at the vault root, generated by the pure functions `formatDirBreakerReportNote`/`formatFileBreakerReportNote` in `src/ui/breakerReport.ts`): `nextcloud-sync-dir-breaker-report.md` for the directory side (by `deleteRemote`/`trashLocal` category, with counts, all entries without truncation) and `nextcloud-sync-file-breaker-report.md` for the file side (all entries, without truncation). **Bug fix**: before the fix, clicking the error row ran `openLinkText` on the pseudo-label string itself (for example `(dir mass-delete breaker)`), so an empty note with that name was created by mistake. These report notes are fixed-name diagnostic snapshots overwritten each time, and are excluded from sync by `isSystemExcluded` (the same reason as the own-host log exclusion `isActiveLogFile`).
  - **Only the directory side provides a bulk-resolution action** (the file side is out of scope; the report note only lets the user confirm all entries): `SyncEngine.resolveAllSkippedDirs(choice: 'remote' | 'local')` applies `SyncEngine.resolveSkippedDir(path, category, choice)` sequentially to every path in `dirBreakerSkipped` of the `(dir mass-delete breaker)` error of the latest session (no one-by-one UI operation is provided — the freedom shown to the user is only the two choices "Use remote" and "Use local" plus the single bulk operation Apply). `choice='remote'` matches local state to the remote, and `choice='local'` matches remote state to local (symmetric to the meaning of the existing file-conflict resolution). For `category='deleteRemote'` (absent locally, present remotely): remote -> restore with a local `mkdir` / local -> run `deleteCollection`. For `category='trashLocal'` (present locally, absent remotely): remote -> run `trashFile` / local -> restore with a remote `createDirectory`. A restored directory is tracked by `stateDB.setDir({ path, remoteFileId: null })`, and the real PROPFIND of the next full scan refills `remoteFileId` (the same self-healing pattern as `createSingleFolder`/`renameSingleFolder`). It is mutually exclusive with a running sync through the `this.running` guard. After completion it mutates `this.lastSummary.errors` in place (on full success the error is removed; on partial failure `dirBreakerSkipped` is narrowed to the failed entries only) and reflects it in the dialog immediately without waiting for the next sync. The Sync status dialog shows a bulk-operation row (dropdown + Apply, one row only) directly under the relevant error row, and `main.ts` handles the confirmation modal (consent to a destructive operation) -> the `resolveAllSkippedDirs` call -> a result-count Notice -> redraw (the same division of responsibility as the bulk conflict resolution).

## §8a. Directory sync

### §8a.1 Directories are first-class entities (DP — Directory Propagation)

**A directory is a first-class entity symmetric to a file** and is tracked in `StateDB.directories`. The heuristic "delete if it has 0 child files" has been rejected — an empty directory is a legitimate entity and is kept and synced.

Differences in directory existence are handled by `SyncEngine.reconcileDirectories` only during a full scan (in a token-diff pass, absence cannot be read as deletion).

| State (L: local, R: remote, T: tracked in StateDB) | Action |
|---|---|
| L & !R & !T (local only, untracked) | MKCOL on the remote (empty directories are created too) |
| !L & R & !T (remote only, untracked) | mkdir locally |
| !L & R & T (tracked, gone locally) | DELETE on the remote (only when the `isRemoteDirEmpty` probe passes) |
| L & !R & T (tracked, gone remotely) | trash locally |
| L & R (present on both sides) | keep tracking (`setDir`) |
| !L & !R & T (gone on both sides) | drop tracking (`deleteDir`) |

Safety constraints:
- **Operation order**: CREATE goes parent -> child (shallow-first); DELETE goes child -> parent (deep-first).
- **Data-loss prevention probe**: immediately before `deleteCollection`, `isRemoteDirEmpty` (a Depth:1 PROPFIND) is run, and the delete is skipped if the directory is not empty (self-heal).
- **Existence check before local trash (`DTV-1`/`DTV-2`, GitHub issue #46)**: for a folder classified as `trashLocal`, **immediately before `fileManager.trashFile`, ask the server whether it really exists with `remoteExists` (a Depth:0 PROPFIND)** and move it to the trash **only on a clear 404**. If it exists, or cannot be determined (a network error, the client rejecting), **do not delete and keep the tracking**, and log `dir-sync: listing omitted <path> but the server still has it — keeping it`. Rationale: the `createSingleFolder` of watch mode calls `setDir` right after MKCOL, so if that folder is momentarily missing from the next full sync's listing it falls into `L && !R && T`, and **one folder = one deletion stays under the mass-deletion breaker threshold** while the folder was deleted together with its contents (issue #46). This aligns the folder side with the principle that `applyLocalDeletion` on the file side requires a proof of "delete only when the server checksum matches the base". The classification (`classifyDirectories`) is left a pure function, and **the proof is required on the execution side**. The round trip is 1 per `trashLocal` candidate, and 0 when there are no candidates. The root cause of the missing listing is not yet identified, pending the reporter's reply (the short-circuit rebuild is not the cause, since it includes the directory table of State).
- **The plugin's own trash is not a "local deletion" (`DTV-3`, GitHub issue #46)**: when moving a folder to `.trash` **succeeds**, all tracking under `<path>/` is dropped at the same time — the state, merge base and clean-side snapshot of the files, the tracking of subdirectories, and the folder's own dir row (the single sink `src/sync/deletion/subtreeTracking.ts`). It applies to `DirectoryReconciler.trashLocal` / `resolveSkippedDir` and `DeletionService.processRemoteDeletion` (all callers: sync-token diff, absence deletion, Mirror). **If the trash fails (an exception), nothing is dropped** (retry next time; the same principle as `G1-2`).
  - **Rationale (the amplifier of this issue itself)**: `trashFile(folder)` moves the folder to the trash **together with its contents**, but the old implementation dropped only `deleteDir(path)`. The remaining tracking of the files below was read at the next sync as "tracked, absent locally" = **the user deleted it locally**, and propagated to the server as a DELETE. That is, a down-direction erroneous deletion (a missing listing) was **amplified into a real deletion** in the up direction (the reporter's symptom "it disappears from both the local `.trash` and Nextcloud's 'Deleted files'"). The existence check (`DTV-1`/`DTV-2`) closed the entrance (not in the listing -> immediate trash), but the amplifier remained.
  - **Why dropping the tracking is acceptable**: if the trash is legitimate (the server really returns 404), the contents are also absent from the server, so dropping is harmless; if the trash is illegitimate (the listing omission was a lie), dropping makes them **revive** at the next sync as "new on the remote". Either way it is safer than "not dropping" (self-healing).
  - **Prefix rule**: what is dropped is `p === <path>` or `p.startsWith('<path>/')`. `F2/...`, `F.md` and `FF/...` are not affected. If `<path>` is the empty string, nothing is done (the vault root is never wiped).
  - **Preventing backflow into watch mode (an order-independent two-layer defence)**: `trashFile` fires vault `delete` events for the files and folders below, and their delivery timing is independent of the resolution order of `await`. So (1) **before the trash**, register the folder itself and the tracked paths below it in `LocalAdapter.ignore()` (the existing `isOwnSyncEvent` mechanism, a 5-second window), and (2) use the tracking drop after a successful trash as the second barrier (events that arrive after the window closes also return early: `deleteSingleFile` on an untracked file, `deleteSingleFolder` on an untracked dir). It does not depend on `isSyncRunning()` — because **`applyRemoteMirror` does not set `running`**, so it would not work for a trash originating from Mirror. In addition, the same `isSyncRunning()` early return as `deleteSingleFile` was added to `deleteSingleFolder` (the highest-impact sink, since it issues a recursive `deleteCollection`, yet the only one that had no guard).
  - Tests: `GDP-1` to `GDP-3` (a; pure functions for prefix and 3-store discard), `GDP-4` to `GDP-7` (a; `DirectoryReconciler`), `GDP-8` to `GDP-13` (a; engine integration), `GDP-30`/`GDP-31` (b-1).
- **Mass-deletion circuit breaker**: bulk deletion is refused when `deleteRemote.length + trashLocal.length > massDeleteLimit(denom)` (prevents a misjudgment from a partial listing). CREATE continues even after the breaker fires.
- **Locking**: **file locking is fixed to always off** (the `fileLockingEnabled` setting was removed). A remote DELETE is not wrapped in lock/unlock (`acquireLock` always returns null because `FIXED.fileLockingEnabled === false`). Lost-update safety is guaranteed by the always-ON If-Match precondition. The lock implementation is left in place in case it is re-enabled, but the normal path does not reach it. Tests: `DP-13` (delete without a lock), `DP-14` (self-healing continues on failure).
- **self-healing**: a single failure is skipped and normalizes at the next sync. When the listing fails, the whole session is skipped.
- **System exclusion**: `isSystemExcluded` (`.obsidian/plugins/<id>` and the like) is outside the scope of create/delete.

Tests: `DP-1` to `DP-15` (`tests/a-no-nextcloud/sync/dirSync.test.ts`), `DP-e2e`, `DP-e2e-empty` (`tests/b1-nextcloud-headless/sync/emptyDirEngine.b1.test.ts`).

### §8a.2 Directory rename convergence (DR — Directory Rename)

A directory rename has no dedicated MOVE instruction; it converges naturally through a combination of **file-level hash-match rename detection (`RenameTracker.detectLocalRenamesByHash`) + create/delete reconcile of directories**.

- **DR-local**: when device A renames `old/` -> `new/` locally, the files below match by hash -> WebDAV MOVE; the old directory gets `deleteCollection` after the `isRemoteDirEmpty` probe; and the new directory starts to be tracked with `setDir`. No data loss.
- **DR-concurrent**: when A renames `1111/` -> `2222/` and B independently creates `2222/other.md` — A's sync MOVEs the file and deletes `1111/`; B's sync uploads `2222/other.md` and fetches `2222/file.md` -> both devices converge to the union in `2222/`. Same-named files are handled by ordinary conflict resolution (§6). No data loss.

Tests: `DR-local`, `DR-concurrent` (`tests/b1-nextcloud-headless/sync/dirRename.b1.test.ts`).

### §8a.3 Migration note for existing orphans

Empty directories accumulated by an old bug (for example the `2011` to `2025` year folders remaining on the remote and on the iPhone side) are, at the first sync of the tracking model, "an untracked remote-only dir -> duplicated locally with mkdir" (the empty directories are expanded onto each client). If the user then deletes one on any client, it is thereafter propagated correctly as a dir deletion. This is accepted as the specification (a consequence of rejecting the emptiness heuristic).

### §8a.5 Full-scan optimization by root-ETag short circuit (ES)

**Motivation**: the Nextcloud files DAV returns 415 for the sync-collection REPORT (§18 F1), so **a full scan runs every time** even after the initial sync (`getFiles('')` + `getDirectories('')` at Depth:infinity). Measurement on a real device shows that the current full scan takes 2 round trips, about 641KB and 1757ms. Most syncs have "no remote change", and this is where a short circuit can help.

**Core idea**: Nextcloud propagates the parent directory ETag up to the root on any change below. The ETag of the vault root is therefore a single signal for "did anything change on the remote". On the full-scan path, before `getFiles('')`, fetch the root with **PROPFIND Depth:0**, and if it matches "the root ETag of the last **real** full scan" stored in StateDB, rebuild the remote listing from StateDB (`files`/`directories`) and skip the infinity PROPFIND and `getDirectories('')` (the short circuit).

**Safety (deletion safety is not touched at all)**: the short circuit switches only "where the remote listing comes from". The rebuilt listing is fed to the existing logic as a **complete enumeration** (all tracked files/dirs) with `isFullScan=true` kept, so `processRemoteFile` (all remoteChanged=false -> no download), the upload of local changes, the propagation of local deletions to the remote, the massDelete breaker and conflict resolution work correctly **unmodified**. The RemoteFileInfo rebuild restores checksum (sha256)/etag/size according to `idType` and matches base.remoteId.

**Self-heal**: the stored root ETag is updated **only when a real full scan completes**. A local upload/delete/rename within a short-circuited sync changes the remote ETag, so the next Depth:0 mismatches and automatically returns to a real full scan. As a countermeasure for the rare "untracked remote file" drift, after `FORCE_FULL_SCAN_EVERY = 20` consecutive short circuits (`src/util/limits.ts`, not a user setting), a real full scan is forced and the counter is reset to 0.

**Convergence-gate invariant (data safety, mandatory)**: the short circuit may be armed only when "**the previous real scan fully converged (StateDB == remote)**". If a real scan **ended unresolved** (`safe-hold` / conflict markers, an error, a leftover retryQueue), StateDB.remoteId can stay diverged from the real remote (nothing was pushed, so the remote root ETag is unchanged). Short-circuiting in that state would mistake the rebuilt remote listing (= the stale StateDB) for reality and **silently overwrite the unresolved remote change with local-wins = losing the other device's edit**. To prevent this, **if in one session any of `conflictedCount>0` / `errorCount>0` / a non-empty `retryQueue` holds, the stored root ETag is invalidated to null**, so the next time a real full scan is always run (re-armed by a real scan after convergence).

> **Special case for the tie no-op (ES-11, data safety)**: a **tie (no-op)** of `biggest-size`/`latest-mtime` **counts as "success", increments no counter**, and intentionally leaves both sides divergent (local≠remote, StateDB unchanged, no push = remote root ETag unchanged). The convergence gate above (a counter check) therefore cannot catch it, and **the short circuit stayed armed, so the next sync rebuilt from the stale StateDB, misread the tie as local-only and silently uploaded local = losing the remote (another device's edit)** (the old bug). The countermeasure: **the `no-op` branch of `handleConflict` itself calls `setRemoteRootEtag(null)`** to disable the short circuit, so the next real scan detects the tie again (self-healing). Tests: the strategy matrix (the merge=markers / biggest-size=tie cases of `tests/b1-nextcloud-headless/multidevice/conflictPolicyMatrix.b1.test.ts`) detects and pins the regression, and the layer-a `ES-11` (asserting the `setRemoteRootEtag(null)` call in the tie cases of `syncEngine.test.ts` / `configFolder.test.ts`) is a fast regression guard.

**Applicability and fallback**: Nextcloud only (`features.isNextcloud`). `StandardWebDAVClient.getRootEtag` returns `null` and always behaves as before (plain WebDAV does not guarantee root-ETag propagation). The initial sync (empty state), a missing stored root ETag, a failure to fetch the root ETag, and a forced FS arrival do not short-circuit and run a real full scan. **Zero added user freedom** (the only new internal state is `remoteRootEtag` and the short-circuit counter; old state lacking them is backward compatible via a real full scan).

> **The short circuit does not resurrect deleted files**: the rebuild source is StateDB, and once an absence deletion is applied that entry disappears from State. The listing rebuilt by the next short circuit therefore contains no ghosts. Conversely, **if a deletion was skipped it stays in State and is rebuilt as "present on the remote", which would obstruct self-healing**, so the absence deletion of §8 running regardless of the listing count is also a precondition of the short circuit. Test: `EAD-2`.

Tests: `ES-1` to `ES-10` (`tests/a-no-nextcloud/sync/rootEtagShortcircuit.test.ts`). The real-device e2e is `tests/b1-nextcloud-headless/sync/rootEtagShortcircuit.b1.test.ts`, and the effect measurement is `tests/b1-nextcloud-headless/perf/etagSkip.perf.b1.test.ts` (for reference).

### §8a.6 Future idea (out of scope)

Speeding up the diff of a **partially changed subtree** with a Composite/Merkle tree (`Dir.checksum()`) (recursively scanning only the changed paths). Real-device measurement showed that for a single deep change the time got worse because of the added round trips (scenario D), and the "skipped subtree" invariant would spill over into remote-deletion detection (the most dangerous path) and complicate it, so it is **not adopted**. This optimization is limited to the single-root-ETag short circuit of §8a.5. If it is reconsidered, treat it as a separate specification.

## §9. File-operation safety

Self-event suppression by the IgnoreList (cleared automatically after a 5-second timeout) / atomic download (temporary file -> rename; naming rules are in §9.3) / absolute precedence of system exclusion (`.obsidian/plugins/<id>/**` and the plugin's temporary files `isSyncTmpPath` take precedence over user exclusions). Path-traversal defence (`isSafeVaultRelativePath`, test `UP-5`).

### §9.1 Self-sync exclusion of the active log file (`LOG-1`)

**While `loggingEnabled` is ON (the log toggle is unified into one), "this device's own (own `host`) log file", which is its output target, is excluded from sync** (a system exclusion; `isActiveOwnLog` -> `isSystemExcluded`).

- **Target**: this device's single log file `nextcloud-debug_<host>.txt` (when `loggingEnabled:true`; logs are consolidated into one file, see §12). It is judged by the real path that the output target resolves to, fixed at the vault root (`logsFolder`='').
- **Reason**: the plugin appends to this file during sync. If it were a sync target, (1) the rename of an atomic write would race with the live append and Obsidian would throw `Destination file already exists!`, and (2) the self-trigger "log write -> file change -> next sync target" would **churn forever**.
- **The exclusion is intentionally minimal in scope**:
  - **When the toggle is OFF** the file is static and **returns to being an ordinary sync target** (not excluded).
  - **Logs of other devices (another `host`)** are not written on this device and are therefore **not excluded** (cross-device log collection is preserved; the host-name suffix avoids collisions).
- Tests: `LOG-1` (`tests/a-no-nextcloud/sync/logSelfSync.test.ts`, `tests/a-no-nextcloud/sync/logging/logPaths.test.ts`).

### §9.2 Download safety guards

- **Server-anomaly defence (empty-body guard / `SG-1` to `SG-4`)**: before applying remote content locally, only when the GET body comes back **empty (0 bytes)** for a file for which the server declared **>0** in PROPFIND, it is treated as a "server anomaly" (an S3 mount inconsistency, an erroneous 0-byte return and so on) and the **overwrite is refused** (`isAnomalousRemoteContent` = `remoteSize>0 && received===0`, `src/util/limits.ts`). Local and Base are unchanged; an error is recorded and retried (self-heal). **A legitimate emptying of a file (declared 0, body 0) is not falsely detected.** It applies to download (remote-modified) and prefer-remote (conflict resolution).
  - **A non-zero size mismatch is not treated as an anomaly (correction; important)**: on a real iOS device, the Obsidian `requestUrl().arrayBuffer.byteLength` does not match the server's content-length (for example 1948 -> 1949, enlarged for multibyte content; the server itself was confirmed on a real device to be consistent: PROPFIND == GET == actual bytes). The original judgment "declared ≠ received is always an anomaly" rejected a large number of legitimate downloads (missed remote -> local sync), so it was limited to **an empty body only**. Tests: `SG-1` to `SG-4` (`tests/a-no-nextcloud/sync/downloadSafetyGuards.test.ts`).
- **Write read-back verification (`WB-1`/`WB-2`)**: after the rename, `LocalAdapter.atomicWriteBinary` verifies with `stat` that the actual size equals the intended byte length, and throws an exception on a mismatch or when the file is missing (best-effort, since Obsidian's adapter cannot fsync. A corrupt write is not mistaken for "success" and Base is not advanced). Tests: `WB-1`/`WB-2` (same as above).

### §9.3 Temporary-file naming and handling of long file names (`TN-1` to `TN-8`)

An atomic write (`atomicWrite` / `atomicWriteBinary`) is a "write to a temporary file -> rename" scheme. **The temporary file name must not depend on the length of the final file name.**

- **Background**: the file system limits one path component to `NAME_MAX` (ext4/F2FS = **255 bytes**; bytes, not characters). The old implementation named the temporary file `final path + '.nextcloudsync.tmp'` (+18 bytes), so **even when the final name was within 255 bytes the temporary name exceeded 255 bytes**, and on Android download failed with `FILE_NOTCREATED` (`ENAMETOOLONG`) (the boundary is 255 - 18 = 237 bytes; one Japanese character in UTF-8 is 3 bytes).
- **Temporary-file naming (`TN-1` to `TN-5`)**: the temporary file is placed **in the same directory as the final file** with a fixed-length short name `.<hash>.ncs.tmp` (a hidden file) that uses a deterministic short hash derived from the target path (`tmpPathFor`).
  - The temporary name length is fixedly small and **independent** of the final name length (`TN-2`). Every ancestor directory component is guaranteed to be ≤255, so the temporary name is always ≤255 -> **if the final name is within 255 bytes the write always succeeds** (`TN-1`).
  - Different targets get different temporary names (no collision even for concurrent writes in the same directory, `TN-3`), and the same target is stable (deterministic, `TN-4`).
  - **Atomicity is preserved** by a rename within the same directory (never a cross-directory rename, `TN-5`).
- **Error conversion for an unavoidable length excess (`TN-6`/`TN-7`)**: when the final file name itself exceeds 255 bytes, it is unavoidable at the OS level. Catch the native error thrown by the write/rename (reactive; there is no up-front byte-length gate), measure the UTF-8 byte length of the final name, and convert it to an easy-to-understand message meaning "**File name too long (NN bytes / max 255 bytes). Shorten the file name.**" shown in the error list of Sync Status (`translateNameTooLong`, `TN-6`). Other errors (such as the read-back verification failure `WB-2`) for a final name within 255 bytes are **rethrown without conversion** (a normal failure detection is not swallowed, `TN-7`).
- **Old/new compatibility of temporary-file detection (`TN-8`)**: `isSyncTmpPath` matches **both** the new suffix `.ncs.tmp` and the old `.nextcloudsync.tmp` (leftovers from older versions are still ignored by the watch ignore and ignored/cleaned by `removeTmp`). Only the new naming is generated. On failure the temporary file is cleaned up in a catch so no leftovers remain.
- **self-healing**: a long-named file that failed under the old implementation is fetched automatically at the next sync and disappears from the error list of Sync Status. Tests: `TN-1` to `TN-8` (`tests/a-no-nextcloud/data/localAdapterTmpName.test.ts`).

### §9.3a Hard exclusion of machine-managed folders (`EXCL-HARD-1`)

**`.git` and `.trash` are always outside the sync scope, regardless of the user's `excludedFolders` setting** (a permanent hard exclusion; judged inside `isSystemExcluded` by `HARD_EXCLUDED_FOLDERS` (`src/util/excludedFolders.ts`) with the **folder-boundary match** of `isUnderExcludedFolder`).

- **Reason**:
  - `.git` — a machine-managed repository. Syncing it file by file corrupts the repository (real damage in discussion #6).
  - `.trash` — Obsidian's device-local trash (where deleted notes go when "Deleted files" is set to "Move to Obsidian trash"). Syncing it would clutter every device's trash and would churn with the plugin's own `trashFile`-based deletion (remote deletion -> move to local `.trash` -> re-upload). Restoring a remote deletion is handled by the Nextcloud server-side trash, so double management is unnecessary.
- **A fixed, narrowed list, not a blanket "exclude all dotfolders"**: other root dot content that `collectDotPaths` syncs (`.archive/`, `.env` and so on) **is still synced**. Because the match is a folder-boundary match, sibling names that merely share a prefix (`.github/`, `.trashcan/`) and files (`.gitignore`) are not excluded.
- **`collectDotPaths` also skips early**, stopping a wasteful recursive enumeration of a huge `.git/` tree.
- **The meaning is "ignore", not "delete"**: a `.git`/`.trash` that is already on the remote is not deleted but left alone, and no longer takes part in sync (`isSystemExcluded` also removes it from the scope of deletion candidates). Manual deletion on the server is possible.
- The settings UI (tooltip and description) has long said "dotfolders (`.git` and so on) are excluded by default", and with this clause the **implementation follows the explicit contract**.
- Test: `EXCL-HARD-1` (`tests/a-no-nextcloud/sync/hardExcludedFolders.test.ts`, `tests/a-no-nextcloud/network/dotPaths.test.ts`).

### §9.4 Download size guard (`DSG-1` to `DSG-8`, issue #8)

**The "Maximum file size" setting (`maxFileSizeMB`) applies symmetrically to downloads as well as uploads.** The judgment is centralized in the single function `isOverFileSizeLimit` (`src/util/limits.ts`) shared by upload and download, and only the consequence depends on the path. The threshold rule is the same as upload (exactly the limit is allowed; skipped if even 1 byte over; `maxFileSizeMB=0` is unlimited).

- **Background (issue #8)**: download had no size check and expanded the whole remote body into memory unconditionally. On Android, Obsidian `requestUrl` Base64-encodes the whole response body before handing it to JS, so a GET of a large file (about 83MB in issue #8) caused an `OutOfMemoryError` -> an app crash.
- **Canonical size (FR-001a)**: the size check before download uses **the server-declared size `RemoteFileInfo.size`, already obtained at sync-planning time from the WebDAV PROPFIND `getcontentlength`** (no additional request and no prefetch of the body). This declared size is the **source of truth for the size guard**, and the judgment uses it even if there is a slight difference from the actual downloaded byte count (the same root as the iOS byteLength mismatch of §9.2). A remote with an undeclared or 0 size is not skipped for size reasons (the other guards apply as usual).
- **Applied to every download path (FR-005; the consequence depends on the path)**:
  - **(a) ordinary remote -> local import / (b) restoration import for local deletion vs remote edit** (the guard at the top of `downloadFile()`): skip without issuing a GET, plus a notice. No retry (a permanent skip), not counted as an error, and **local/Base are preserved** (self-healing). `DSG-1`/`DSG-2`.
  - **(c) remote fetch during conflict resolution** (the guard at the top of `handleConflict()`, FR-010): do not fetch the remote; keep the local content and make it visible with **`isConflicted=true`**. No retry; Base preserved. It converges on a re-sync after the limit is raised. `DSG-3`.
  - **(d-1) diff preview / Compare** (`compareWithRemote()`, FR-011): return metadata only without fetching the body (`remoteText=null`, `diffAvailable=false`) plus a notice. `DSG-4`.
  - **(d-2) manual pull** (`pullRemoteToLocal()`, FR-011): throw a clear `Error` indicating the size excess (notified to the UI). `DSG-5`.
- **Permanent skip (FR-004)**: a size-excess skip is not put on the retryQueue and is not counted in the sync error count (an intentional, setting-derived skip, not a transient failure).
- **self-healing convergence**: a skip leaves only a temporary inconsistency, and **raising the limit and re-syncing imports the file and restores consistency** (no permanent corruption or sync stall). `DSG-8`.
- **No new user setting is added (FR-007)**: it only widens the scope of the existing single `maxFileSizeMB`. With the desktop default 0 (unlimited), download behaviour is unchanged (FR-008, `DSG-6`). Boundary = a file exactly at the limit is imported (`DSG-7`).
- Tests: `DSG-1` to `DSG-8` (`tests/a-no-nextcloud/sync/downloadSizeGuard.test.ts`, 8/8 GREEN). Regression: `downloadSafetyGuards` (§9.2), `uploadStrategySelection`.

### §9.5 Preserving the display of open files (GitHub issue #15)

**When a sync updates the content of an existing file and that path is currently open in any leaf (a `FileView`-family view; text or binary, all of Markdown/image/PDF and so on), `LocalAdapter.atomicWrite` / `atomicWriteBinary` do not use tmp-write -> remove -> rename and instead perform an in-place update with Obsidian's official `Vault.modify` / `Vault.modifyBinary`.**

- **Background (issue #15)**: the previous `atomicWrite` / `atomicWriteBinary` was a physical delete+recreate: "write to a temporary file -> delete the existing target with `adapter.remove()` -> restore with `adapter.rename()`". This delete event reached the Obsidian core and switched the view of the leaf showing that file to an empty pane (`viewType: "empty"`), so the note being edited looked "closed" (reproduced and confirmed in the real Obsidian UI with `tests/b2-nextcloud-ui/scenarios/activeLeafSurvivesSync.b2.test.ts`).
- **Detection (`OL-1`/`OL-2`)**: with the `Workspace` reference held by `LocalAdapter` (an optional constructor argument; production always injects `app.workspace`), walk `iterateAllLeaves`, and if one or more leaves are a `FileView` whose `file.path` matches the target path, it is judged "open". Because the view type is not restricted, the effect is identical for text (`OL-1`) and binary attachments (`OL-2`). Even when the same file is open in multiple leaves, the Vault shares a single `TFile`, so one `modify`/`modifyBinary` is reflected in all leaves.
- **A deferred leaf is also judged "open" (`OL-4`, GitHub issue #32)**: since Obsidian 1.7.2, **a leaf of a background (inactive) tab holds a `DeferredView` instead of its real view** (`WorkspaceLeaf.isDeferred`). `DeferredView` does not extend `FileView` — by unpacking the distributed binary (`app.asar` / Obsidian 1.13.4) it was confirmed that `isDeferred` is in fact `this.view instanceof <DeferredView>` and that the identifying members of `FileView` (`onLoadFile` / `allowNoFile` / `this.file`) are entirely absent from its prototype chain. `instanceof FileView` alone therefore **misses a note open in a background tab**, falls into the destructive tmp-write -> remove -> rename path, and the leaf lost the file (= the same "looks closed" symptom as issue #15 remained on background tabs). The detection additionally uses a path that resolves a `TFile` with `Vault.getFileByPath(path)` when `leaf.isDeferred` holds and `leaf.getViewState()?.state?.file` matches the target path. If `getFileByPath` returns `null` (a folder, a deleted file and so on), it is treated as "not open" and falls back to the `OL-3` path (it never mistakes a file for open). It works for both text and binary.
- **When not open (`OL-3`)**: when `workspace` is unset (in tests and so on), or no leaf has the target path open, the existing tmp-write -> remove -> rename path (including the crash safety of G4-1 and the read-back verification of `WB-1`/`WB-2`) is used completely unchanged. The retry/self-healing behaviour (§9.2 and so on) is also unchanged.
- **Callers are unchanged**: the branch is confined to one place inside `LocalAdapter`, and the calling code of `SyncEngine` (6 places) and `ConflictResolver` (1 place) is not changed. No new user setting or choice is added.
- **Known remaining path (a rename arrives as a deletion)**: the engine keeps `remoteFileId` (Nextcloud's `oc:fileid`, which does not change on rename) for each file, but **rename detection is not implemented**, and there is no call to `Vault.rename` / `FileManager.renameFile` for user files. A rename or move on another device is therefore applied as "deletion of the old path" plus "creation of the new path", and if the old path was open, `processRemoteDeletion` runs `fileManager.trashFile` (this sink never looks at the state of the leaf). As a result the tab goes back one step in its history. **The in-place update of `OL-1` to `OL-4` above cannot prevent this** (it is the deletion path, not the write path). It is pinned as current behaviour by `T7`, and changing it requires a design decision on rename detection.
- Tests: `OL-1`/`OL-2`/`OL-3`/`OL-4` (`tests/a-no-nextcloud/data/localAdapterOpenLeaf.test.ts`), `T7` (`tests/a-no-nextcloud/sync/deletion.test.ts`). Real-device proof: `tests/b2-nextcloud-ui/scenarios/activeLeafSurvivesSync.b2.test.ts` (`[issue-15]`, b-2).
## §10. State database

- `state-{deviceId}.json` is saved atomically (write to a temporary file, then rename). **State is isolated per deviceId**, which prevents conflicts when several devices share one vault.
- On corruption or loss the plugin **starts with an empty state** (on a JSON parse failure it logs a warning and falls back to an empty state; there is no dedicated recompute-and-recover routine). An empty state also means `syncToken` is null, so **the next sync runs as a full scan (recompute every SHA-256 plus a remote PROPFIND), which effectively rebuilds the state**.
- **Multi-device convergence**: every device has its own state database and its own deviceId. A late-joining device (empty state) fetches the existing remote content; a reinstall (state lost) re-matches files by the stable `oc:fileid` and does not create duplicates; concurrent edits are protected against lost updates by the If-Match 412 response. Tests: `MD-1`, `MD-2`, `MD-3` (real server).
- **Interrupt and resume**: resuming after an interrupted sync converges from the remaining work, with no corrupted state database and no double application. Tests: `PR-1`, `PR-2`.
- **MergeBaseStore**: `merge-base-{deviceId}.json` is saved atomically (temporary file, then rename) as a **separate file** from the state database, to avoid bloating it. It maps path to the last-synced body (the 3-way merge base). On corruption or loss it starts empty and is re-seeded at the convergence points (self-healing). `MergeBaseStore.load` is lazy (it does not eagerly read at the first seed). Test: `MB-12` (persistence).
- **Fields for the root-ETag short-circuit (§8a.5)**: the state keeps `remoteRootEtag` (the vault-root ETag recorded at the previous real full scan; absent means not recorded, so a real full scan runs) and `fullScanSkipCount` (the number of consecutive short-circuits, reset to 0 every `FORCE_FULL_SCAN_EVERY`). Both are optional and backward compatible with older state files. Test: `ES-9`.

### §11.1 Remote URL encoding (`URE-1` to `URE-5`, GitHub issue #25)

- **A single method (`encodeRemoteUrl`, `src/network/remotePath.ts`)**: split the remote path on `/`, **encode each segment with `encodeURIComponent`**, and join the segments with `/` again. ASCII structural characters such as the space, `#`, `?`, `%` and `&`, as well as non-ASCII characters (CJK, emoji), are all percent-encoded exactly once. `/` is kept as the separator, and because processing is per code point, surrogate pairs (emoji) are never split. **The function takes no argument that identifies the platform**, so it cannot express "change the behaviour only on iOS". Its output is identical to `encodePath()` of `webdav-client`, and the same approach is shipped at scale to iOS users by remotely-save.
- **An earlier decision was wrong and must not be reversed again**: that decision held that the iOS request layer re-encodes the whole URL, so the URL must not be pre-encoded, and it sent raw (unencoded) paths on iOS only. Issue #25 refuted this: the iOS request layer **does not encode a raw space**, so every path containing a space failed with HTTP 404 (the same report showed that a raw `&`, which is a legal URL path character, synced fine, which pinned the failure on the space). The observation that supported the earlier decision, that a pre-encoded `%20` becomes a literal `%20` name on the server, can also be explained by **double encoding in a reverse proxy** (nginx rebuilds the URI from the normalized, already-decoded form when `proxy_pass` carries a URI; Apache documents that `RewriteRule` without `[NE]` double-encodes existing percent-encoding). The clients of both reporters are almost identical (Obsidian 1.12.7 on iOS 26.5.x), so the difference most likely lies on the server side. **If literal `%XX` names are reported again, check the reverse-proxy configuration before touching this function.** Reverting the method would bring issue #25 back for all users.
- **Server URL normalization (`URE-4`, `encodeServerUrl`)**: the configured Server URL may end in an arbitrary subfolder (which may contain spaces or non-ASCII characters), so **`encodeURI` is applied only when the value contains no `%`**. A value that contains `%` is assumed to be an already-encoded URL pasted by the user and is left untouched (this prevents `%20` from becoming `%2520`). The value stored in the settings is never rewritten.
- **Scope (`URE-2`)**: every path that builds a remote URL goes through the same method: GET, PUT, DELETE, PROPFIND, REPORT, PATCH, MKCOL, MOVE, and also **the `Destination` header of MOVE** (including the one used when a chunked upload completes). Header values are not encoded by the request layer, so a raw value must never be put there. Version-management URLs (which carry only the opaque IDs `fileId` and `versionId`) are out of scope. Send/receive symmetry (`URE-3`): `decodeURIComponent` in `hrefToRelative` is the inverse transform, so the round trip is the identity.
- **Diagnostics for network failures (`URE-5`)**: `NetworkError` keeps the failing HTTP method, and its message is `HTTP <status> (<METHOD>)` (when the method is not given it stays `HTTP <status>`, so **prefix matching is preserved**). The response body is not included in the message (logs get pasted into public issues). When a sync finishes, `SyncEngine.logSessionErrors` writes **every collected error, one per line and with its path,** to the debug log (**with no cap on the count**). In issue #25 only `err=162` was recorded and none of the 162 paths could be identified; this change removes that problem permanently.
- **Verification policy**: the project has no automated test infrastructure for a real iOS device. Layer a proves the pure function, the wiring of every path and the diagnostics (`remotePath.test.ts`, `webdavRoundtrip.test.ts`, `noCacheHeaders.test.ts`, `syncErrorLogging.test.ts`), and **layer b-1 (`encodedPaths.b1.test.ts`) verifies the round trip against a real Nextcloud and the real server-side names (taken from the PROPFIND hrefs)**. Final confirmation on a real iOS device is secured by a beta release first, with **confirmation by both reporters (issue #25 for the space case, PR #17 for the CJK case) as a mandatory gate for the stable release**.

### §11.2 Missing Server URL subfolder (HTTP 409 on MKCOL, GitHub issue #63) (`SU-1` to `SU-4`)

- **Premise**: the Server URL may end in a subfolder (§11.1), and that subfolder must already exist on the server. The plugin creates the vault folder (named after the vault) **inside** it but never creates the subfolder itself: creating a path the user may have mistyped would silently put the vault in the wrong place, and the subfolder is the only way to choose where the vault lives (§1).
- **Symptom**: with a missing subfolder the MKCOL of the vault folder fails with `HTTP 409` (WebDAV: the parent collection does not exist), which used to surface as a bare `HTTP 409 (MKCOL)` with no way to tell the cause.
- **Message (`SU-1`)**: a MKCOL that ends in 409 carries a hint after the unchanged `HTTP 409 (MKCOL)` prefix: "a parent folder is missing on the server. If your Server URL ends with a subfolder, create that folder in Nextcloud first (the plugin does not create it)." It applies to both failure shapes: `mkcolStrict` (vault-root re-creation, `MissingParentFolderError`) and `RemoteDirCreateError` (ancestor creation before an upload). The hint is one constant (`MISSING_PARENT_HINT`), so the notice and the Sync Status listing, which show the same error message, can never disagree. The wording is conditional, not an assertion: a 409 can also mean an ancestor another device just deleted, which the existing single retry already repairs.
- **No hint elsewhere (`SU-2`)**: other statuses (401, 403, 423, 5xx, a thrown request) and other methods keep their messages, and so does the 409 of the chunked-upload session MKCOL (`remote.php/dav/uploads/...`), which has nothing to do with the Server URL subfolder.
- **Behavior is unchanged**: no new setting, no extra request, no change to which folders are created or to retries.
- **Verification**: layer a covers the message shapes and the README statements (`SU-1`, `SU-2`, `SU-4`; `missingParentHint.test.ts`); layer b-1 covers a real server whose Server URL points at a missing subfolder, and the success after the folder is created (`SU-3`; `missingSubfolder.b1.test.ts`). `SU-4`: README.md and README.ja.md state the premise and how to check a 409.

## §12. Logging and device name

- **The Debug section is a single toggle**: the only Debug item the user can change is the `loggingEnabled` toggle. The input UI for `deviceName` and `logsFolder` (text input, Browse) has been removed (`DBG-1`). Both fields remain in `DavSyncSettings` but always hold fixed values (the same "keep fixed values in `DavSyncSettings` too" policy as for other fixed settings).
- **Fixed values** (`DBG-2`): the output location is fixed to the vault root (`logsFolder` = ''), and the host name is derived as `<platform>-<deviceId6>` (`deviceName` = ''). The log level is fixed internally to `verbose` (no UI).
- **Convergence of existing values** (`DBG-3`): a user who saved custom values in `deviceName` or `logsFolder` with an older version also converges to the same path as a new install, because on every load `resetDebugIdentityFields` forcibly resets both to '' (the cleaned settings are saved if there was a custom value). Logs already written to the old folder or under the old file names (`nextcloud-sync_*_<host>.txt`) are neither moved nor deleted (they are left stale; with the toggle OFF they are synced as ordinary files).
- **Logs are consolidated into one file**: log output is controlled by the single `loggingEnabled` toggle. The output is **one file per own device**, `nextcloud-debug_<host>.txt` (**.txt**, vault root, append). It replaces the two files of the older layout (the structured sync log `nextcloud-sync_sync_<host>.txt` and the debug log `nextcloud-sync_debug_<host>.txt`), and `SyncLogWriter` (the structured summary) has been removed. All logs are collected in one file as `FileLogger` debug lines (`- <ISO8601>  [<host>]  v<version>  <message>`). Each sync operation (upload, download, conflict, merge, delete and so on) is recorded by a debug log line inside `SyncEngine`.
  - **The host-name suffix is kept**: `<host>` is appended so that not every device uses the same name (logs of other devices can be synced into this vault and compared; the exclusion in §9.1 applies only to the own host while the toggle is ON).
- **Immediate firing**: the moment `loggingEnabled` is turned ON in the settings screen, `logSettingsSnapshot()` writes a settings snapshot and a Notice shows the destination path (`plugin.logFilePath()`), so the user is never left in a state where turning it ON appears to do nothing.
- **Visible write failures** (`LOG-2`): even if a log write fails, `FileLogger` **does not rethrow** (this guarantees that logging never breaks the main work). The failure is not swallowed, though: it is surfaced through the `onWriteError` callback, and the host (`main.ts`) wires this to a Notice, so the failure is noticeable even on mobile where DevTools cannot be opened. Test: `LOG-2` (`tests/a-no-nextcloud/sync/logging/fileLoggerLevels.test.ts`).
- **Visibility caveat (known Obsidian behaviour)**: a `.txt` file shows up in the file explorer only when "Files & Links > Detect all file extensions" is ON, and it does not appear in the Quick Switcher (which indexes notes only). ## §14. Maintenance

Settings has a Maintenance category. **Vault index reset** (empties the state database; confirmation required; cancel is an undo; no file is deleted; the next sync is a full scan). Last session summary was moved directly under Maintenance.

**Mirror from remote (pull mirror)**: a destructive Maintenance operation (a destructive button) that makes this device's vault an exact mirror of the current remote state. When pressed, it computes a side-effect-free Mirror plan (fetching the authoritative complete remote listing `getFiles('')` without the root-ETag short-circuit), shows "number of downloads / number of local deletions" in a confirmation dialog, and runs only on consent. The execution (a) downloads the files that exist on the remote (new or with different content; a hash match is skipped), (b) deletes the local **files and folders (including empty ones, children before parents)** that are absent on the remote, following Obsidian's "Deleted files" setting (so they are recoverable), and (c) reconciles the StateDB with the remote state so that an ordinary sync right afterwards converges with zero differences (self-healing). It **bypasses the count limit of the mass-delete breaker** (the user explicitly declares the remote to be authoritative), but it **strictly gates on a successful fetch of the complete remote listing**, and aborts with zero deletions when the fetch fails or is partial. Excluded folders and the system exclusions are respected. It is an explicit operation separate from the ordinary sync path (it is not called from auto sync or watch). It works on both desktop and mobile. **Progress display is the same as for the ordinary "Sync now"**, reusing the statusBar surface (a progress bar on desktop; on mobile a single toast of `NoticeStatusBar`, "Syncing... N/total", which is replaced by the result on completion and dismissed automatically; the engine drives `setStatus('syncing')`, then `setProgress`/`tickProgress`, then `setSyncComplete`). **There are two entry points**: (1) the `Mirror from remote` button in Settings > Maintenance, and (2) a `mod-warning` button of the same name next to `Sync now` in the action row at the top of the `Sync status` dialog. The latter goes through the callback `onMirrorFromRemote` injected from `main.ts openSyncStatus()` into `SyncStatusModal` (capability gate: not rendered when not injected), and both call the same `runRemoteMirror()` (the single source of truth, which contains the confirmation modal, the Notices and the `mirrorInProgress` exclusion). There is no duplicated or branched logic, and the dialog re-renders with the latest report after completion. Tests: `SMB-1` and `SMB-2` (DOM rendering and host wiring cannot be built in the jest `node` environment, the same as for BRC_DOM and MDV_DOM, so they are waived to manual quickstart verification and b-2; the real mirror logic is covered by `MIR-1` to `MIR-3`).

### §15.3 Platform-specific first-run defaults

`DEFAULT_SETTINGS` (`src/types.ts`) holds the **first-run defaults of desktop**. `loadSettings()` (`src/main.ts`) applies the platform-specific overrides **only to keys that have no saved value in data.json** (**first run only**; saved values are unchanged, which keeps backward compatibility). data.json is not shared between devices, so the overrides are applied independently on each device.

- **The items whose first-run default differs between desktop and mobile are the following** (the `Platform.isMobile` branch, `applyMobileFirstRunDefaults`). All other keys (`autoMergeFileStrategy`, `configSync` and so on, the values in the §15.1 table) are **common to desktop and mobile**. The startup sync `startupSyncDelaySeconds` defaults to 1 (enabled) and is **common to both platforms** (mobile is also ON, and the toggle was merged into the slider).

| Key | Desktop first-run default | Mobile first-run default | Override condition | Reason |
|---|---|---|---|---|
| `maxFileSizeMB` | `0` (unlimited) | `20` | First run only (saved values unchanged) | An OOM-safe upper limit |
| `syncOnWifiOnly` | `false` | `true` | Same | Mobile defaults to ON to save cellular billing and data (iOS has no API to judge this so it is effectively disabled; on desktop `type` is not exposed so it is also effectively disabled) |
| `watchOnChangeEnabled` | `true` | `false` | Same | Watch on mobile runs only while the app is in the foreground and uses battery and data, so it is opt-in (the default stays OFF even after the runtime guard was removed) |
| `syncIntervalMinutes` | `15` | `0` (manual only) | Same | The OS stops background timers on mobile, so periodic sync never fires (the `!Platform.isMobile` guard of `applyAutoSyncInterval`). The default 0 makes the display of the disabled slider match reality |

- **`networkConcurrency` does not branch by platform.** Both platforms derive it from the device RAM (`resolveConcurrencyDefault`: RAM unknown = **3** / >= 4 GB = **8** / >= 8 GB = **16** / otherwise = **4**). Mobile often lacks `navigator.deviceMemory` and so tends to get an effective **3**, but this is not a "mobile-specific default" (see the note in §5.4).
- An existing user (whose key is already saved in data.json) **keeps the saved value** regardless of device type (the override is first-run only).
- Implementation: the `Platform.isMobile` branch of `loadSettings()` (`applyMobileFirstRunDefaults`) plus `resolveConcurrencyDefault`. Tests: `spec002Features` (invariants of `DEFAULT_SETTINGS`), `tests/a-no-nextcloud/util/mobileFirstRunDefaults.test.ts` (first-run application of the 4 keys and preservation of saved values), and `tests/a-no-nextcloud` (the RAM tiers of `resolveConcurrencyDefault`).

## §16. Obsidian API mapping

WebDAV uses `requestUrl` (`throw:false`, judged by status). Basic authentication is UTF-8 encoded with `TextEncoder` (avoiding the Latin-1 problem of `btoa`; `:` is forbidden in the username). I/O goes through `app.vault.adapter`. Deletion uses `app.vault.trash(file, true)`. Nextcloud error XML (`OC\ServiceUnavailableException` = maintenance / `InsufficientStorage` = quota / `Sabre\DAV\Exception\Locked` = locked, so back off) is parsed and shown as a Notice.

## §17. Nextcloud extensions

- **Login Flow v2**: "Log in via browser" issues an app password automatically and stores it in secret storage. A server that does not support it falls back to manual entry. Tests: `CN-1`, `CN-2`.
- **Polling advances on whichever comes first, the timer or the app returning to the foreground (`LF-1`, GitHub issue #34)**: when the browser comes to the front for approval, the mobile OS stops the timers of Obsidian's webview. The old implementation waited with `await sleep(POLL_INTERVAL_MS)` alone, so the stopped `setTimeout` never fired and **even when the user came back it stayed stuck on that single `await`**, and could not fetch the app password already issued on the server (Login Flow was effectively unusable on Android). The wait for the polling interval is now a race between the timer and an app-resume signal. By default the resume signal is `visibilitychange` of `document` (only `visible`) and `focus` of `window` (replaceable through `PollDeps.onResume`; both globals are absent in the jest `node` environment, so there is an undefined guard). On resume it polls once immediately, which catches the moment right after approval when success is most likely. Resolving the wait is idempotent, and a timer that fires late is a no-op.
- **The cut-off is wall-clock time, not a count (`LF-2`)**: the limit is `POLL_DEADLINE_MS = 20 minutes`. This matches the token lifetime on the Nextcloud side (`lifetime = 1200` seconds in `core/Db/LoginFlowV2Mapper.php`), which guarantees that the plugin **does not give up before the moment the server stops accepting**. The old `MAX_POLLS = 90` (about 3 minutes) was abolished. The loop advances only when the timer fires, so a count limit measures "time spent polling in the foreground" rather than elapsed time, and it stops making sense once the OS starts stopping timers.
- **Version history**: the command `nextcloud-sync:show-version-history` plus `VersionHistoryModal` (list and restore, Versions WebDAV, atomic, prevention of endless conflicts). Tests: `VR-1` to `VR-4`.
- **Chunked upload**: Nextcloud chunked upload v2 (the uploads endpoint). It is **always enabled** (`chunkedUploadEnabled` is fixed on and gated by the server capability), the chunking threshold is `chunkThresholdMB(Platform.isMobile)` (50 on desktop / 20 on mobile), and only files above `maxFileSizeMB` are skipped. Temporary chunks are placed on the server under `uploads/<uploadId>/`, and assembly is a MOVE of `.file` (the final path appears only when assembly succeeds, so it is effectively atomic). On interruption or failure the session is DELETEd so no incomplete file is left (FR-011). The checksum is verified after assembly (FR-012). Tests: `CHK-1` to `CHK-4` / `SZ-1` to `SZ-7` / `FX-2`/`FX-3`.
- **Files Locking** (experimental, default OFF): LOCK, PUT, UNLOCK. When the capability is not supported, it continues without locking. Tests: `LK-1` to `LK-5`.
- Commands: `nextcloud-sync:sync-now`, `nextcloud-sync:show-version-history`.
- **Recommended server version (no functional blocking)**: **Nextcloud Hub 26 "Winter" (server `33`) or later is recommended** for Nextcloud-specific features. However, an older server is **not blocked from connecting or syncing** (connection and sync work on older versions as well; the settings screen shows a recommendation banner and only some features may degrade). A non-Nextcloud or plain WebDAV server falls back to core sync. Because of the secret-storage API, Obsidian `1.13.0` or later is required (`minAppVersion`, which must match between `main.ts` and the manifest).

## §18. Verified live behaviour and known deviations

These were verified against a real Nextcloud running in Docker. They are **not silenced**: they are made visible as waivers (ruling deferred) in the tests (`clauses.ts`, test `coverage.test.ts`).

- **F1**: the server returns 415 to the `{DAV:}sync-collection` REPORT, so `getSyncToken` returns null, **incremental sync is impossible, and every sync is a full scan**. `TK-1`/`TK-2` waiver. It has a performance impact (to be investigated separately).
- **F1a - the REPORT is not sent at all (`SCR-1`, GitHub issue #37)**: the files DAV of Nextcloud does not implement the sync-collection REPORT, and Sabre returns `ReportNotSupported` (that is, **HTTP 415**). `NextcloudClient.getSyncToken()` therefore **issues no request at all and returns null immediately**. It used to send the request only the first time and skip it afterwards through a per-session flag once it saw the 415, but **Nextcloud writes this rejection to its log at ERROR level with a stack trace**, so every time the plugin created a client one error piled up in the administrator's server log (for a request known to fail). If the request is not sent, the log pollution is zero. There is no functional loss ("no token" is a legitimate path on Nextcloud from the start, and the full scan plus the root-ETag short-circuit (§8a.5) take care of it).
  - `getChanges()` is **kept deliberately**. It is unreachable under this clause, but it is the only place that implements incremental sync if a token is obtained, and deleting it would lose that path.
  - `StandardWebDAVClient.getSyncToken()` is `return null` from the start, so the behaviour of both clients now agrees.
- **F2**: a PUT with a missing parent returns **404 (not 409)**, so both clients fire the reactive MKCOL on both 404 and 409. The b-1 harness uses a pre-emptive MKCOL (`ensureParentDirs`) to set up the test precondition, not as a workaround. Test `UP-2`.
- **F7 (fixed)**: when several files under a new nested folder were uploaded in one session, all files failed with `HTTP 404 (PUT)` in about 25% of runs. There were two root causes. (a) Nextcloud returns **423 Locked** (`OCA\DAV\Connector\Sabre\Exception\FileLocked`) to **concurrent MKCOLs** on the same collection (measured: racing two files with raw HTTP failed 3 times out of 6 attempts). (b) `ensureRemoteDir` put the directory into the cache without looking at the MKCOL status, so **a failed MKCOL was remembered as "created" for the whole session** and the reactive recovery did nothing. It was resolved by fixing the single-flight creation and the cache rules in §5.3 "Contract of parent-collection creation". b-1 was confirmed green 10 times in a row (it failed in about 25% of runs before the fix).
- **F3**: files_lock is **owner based**, so a re-lock by the same user does not return 423 (reproducing 423 needs a different user). `LK-4`/`LK-5` waiver.
- **F4 (fixed in 0.7.1)**: the old `Diff3Strategy` misread the output of `merge()` of `node-diff3` (`{conflict, result:string[]}`) as a chunk array, and silently merged frontmatter conflicts as `conflictRegions:0`. **Commit `993de3c` fixed it by switching to `diff3Merge` (`MergeRegion[]` = `{ok}|{conflict}`)**. A frontmatter conflict is now detected as `conflictRegions>0` with full-file markers. It is verified in layer a with the real `node-diff3` (`CF-12` = `tests/a-no-nextcloud/merge/diff3Strategy.test.ts`; the waiver is lifted).
- **F5 (fixed, ruling: option a = conforming to §6.2)**: `ReconcileTextStrategy` (the `reconcile-text` CRDT) **always returns no-conflict (`conflictRegions:0`) by construction**, so the `maxConflictRegions` circuit breaker was **completely dead** for body conflicts, and a mergeable extension with `autoMergeEnabled:true` always produced a clean write. **`MergeEngine.mergeText` was fixed** to adopt the merge result (content) of reconcile and, at the same time, **measure the real `conflictRegions` separately with diff3 and feed it to the breaker**. As a result `maxConflictRegions` (a positive cap) works for body conflicts for the first time, and when `conflictRegions > maxConflictRegions` is exceeded it reaches `conflictFailurePolicy`. **However, `maxConflictRegions` is fixed to 0 (unlimited)**, so in actual operation the region-count cap does not fire and the CRDT merge of reconcile is adopted (the content-loss 50% breaker is always active). The function of a positive cap itself is verified by the MergeEngine unit test `CF-14` (`tests/a-no-nextcloud/merge/mergeEngine.test.ts`), passing the config directly.
  - **A true 3-way merge**: the State DB used to hold only hashes and no base body, so the `base` of a body merge was always empty, and there was a destructive bug where reconcile duplicated blocks shared by both sides ("the same block is repeated"). **`MergeBaseStore` (`merge-base-<deviceId>.json`, a file separate from the StateDB to avoid bloat) now keeps the last-synced body, and `SyncEngine.handleConflict` passes `baseStore.get(path)` as the 3-way base**. The base is recorded at every convergence point (download / first upload / clean merge / prefer-local / prefer-remote) and dropped on deletion (watch alone / applyLocalDeletion / remote deletion of a config dotfile / propagation of a remote deletion). Even when the base is missing or stale, the plugin degrades safely through the inflation guard (FR-005b) plus the convergence seed (self-healing). The first seed is lazy (no eager read). No dedicated capacity limit is set for the base (Option A). `MB-1` to `MB-4` demonstrate the root fix, and `MB-5` to `MB-14` verify convergence, deletion and persistence. When the base is missing, the fallback is, as before, a conservative 2-way detection that runs diff3 with an empty base (`excludeFalseConflicts` treats only regions that differ as conflicts, and a region where both sides agree is not). `CF-2` to `CF-5` are still verified on the autoMerge OFF path as well.
- **F6 (fixed, GitHub issue #51)**: even when the listing PROPFIND returned 207, the body itself (truncated, non-XML, `parsererror`, non-multistatus) was not validated, and `getFiles`, `getDirectories` and `statFile` treated it as an empty array or `null`. On a large vault (588 files) this showed up as a false firing of the file mass-delete breaker, although the reporter's files really existed on the server. On a small vault, versions before the fix may have trashed whole folders (a strong candidate for issue #46, not confirmed). The root cause (why the body was broken, for example a buffer limit in a reverse proxy) is unidentified and waiting for more information from the reporter, but the symptom was stopped by "not trusting an unreadable body", whatever the cause. A validation was added to `parseResponses` in `src/network/dav/propfind.ts`, and an unreadable body is thrown as `RemoteListingUnreadableError`. `ULG-1` to `ULG-18` verify it and demonstrate reachability through the engine with a layer-a double.

### §18.1 Data-safety and concurrency invariants

The defects of priority "high" that a static analysis of all the source confirmed were fixed. The core principle is **"advance the state only on success"** (on failure, carry over to the next sync and converge by self-healing).

- **`G1-1`** (`resolveByWrite`): when the push of a clean merge fails (412, 423, or a momentary disconnect), `isConflicted` is not set unconditionally to `!clean`; **if it has not been uploaded it stays conflicted**. The old implementation fixed `isConflicted:false` even with `uploaded=false`, and mistook the file for "converged" with remoteId = the old value and localHash = the merged value, so the merge result was never sent. Test: `G1-1` (`tests/a-no-nextcloud/sync/resolveByWriteUploadFailure.test.ts`).
- **`G1-2`** (`deleteSingleFile` / `deleteSingleFolder` / the missing-path deletion of local modification / the `statFile` query): StateDB tracking is removed **only when the remote deletion has really succeeded (2xx / 404)**, and **only when the existence check has settled on 404**. On a real failure (423, 500, timeout) the tracking is kept and retried at the next sync (the old implementation removed it unconditionally, so a deleted file was misjudged as "new on the remote" and came back). Test: `G1-2` (`.../singleDeleteFailure.test.ts`).
- **`G4-1`** (`LocalAdapter.atomicWrite` / `atomicWriteBinary`): when `rename` fails after `remove(target)` succeeded, **the tmp file, which is the only copy of the new content, is not deleted** (decided by the `targetRemoved` flag). The old implementation deleted tmp unconditionally in the catch and could lose both old and new. Test: `G4-1` (`tests/a-no-nextcloud/data/localAdapterAtomicWrite.test.ts`).
- **`G4-2`** (`load` of `StateDB` / `CleanSideStore` / `MergeBaseStore` / `SyncHistoryStore`): when a crash between `remove` and `rename` leaves the primary absent and tmp present, **`load()` recovers from tmp** and adopts it (the old implementation saw exists=false, mistook it for "first launch = empty", and discarded the persistent state). Test: `G4-2` (`.../storeCrashRecovery.test.ts`).
- **`G5-1`** (`ChunkedUploadStrategy` / `IWebDAVClient.uploadChunked` / `NextcloudClient`): `ifMatchEtag` is propagated to the main chunked-upload path as well, and `If-Match` is applied to the assembly MOVE (412 becomes `PreconditionFailedError`). This removes the asymmetry in which only large files bypassed optimistic exclusion and could overwrite concurrent edits. Test: `G5-1` (`.../chunkedUploadIfMatch.test.ts`).
- **`G6-1`** (`SyncStatusModal`): force-resolve (per-file and bulk) is guarded by an **instance field that survives re-rendering** (`KeyedBusyGate`) (the old implementation relied only on the `disabled` attribute of the regenerated DOM, so a `render()` during an in-flight run could run it twice). Test: `G6-1`.
- **`G6-2`** (`VersionHistoryModal`): a version Restore is serialized by a per-modal in-flight gate (while version A runs, version B cannot be pressed). Test: `G6-2`.
- **`G7-1`/`G7-3`** (`main.ts` / `SettingTab`): `initSyncEngine()` was made idempotent (before creating a new engine, it runs `stopAutoSync` of the old engine plus a status-bar dispose) and **memoizes the in-flight promise**, which prevents double initialization in the load window. This removes the double creation, orphan timers and double StateDB reads/writes on re-login (confirmed by code review; there is no automated test because of layer-a harness limits).
- **`G7-2` (retired)**: the clause under which watch on mobile was disabled by a runtime guard. It was removed and replaced by §5.7c (`MWM-1` to `MWM-6`).
  - Note: the `maxFileSizeMB` finding of the same analysis was a **false positive** (the slider is editable on mobile too and not disabled, there is no precedent of runtime enforcement like the other existing fields, and a silent clamp would diverge from the UI, so it was not adopted).
- **`G3-1`** (`MergeEngine.mergeBodyByRegions`, empty-base path): when the base is empty, reconcile-text **fuses two divergent edits at character level** (destroying line boundaries and falsely reporting `local` + `remote` -> `localremote` as "clean"). This corruption is detected by **`linesSurvive` (whether every line of each side survives intact and in order in the result)** and routed to conflict. It closes the hole that the length and adjacent-duplicate guards could not catch (pure concatenation, exactly the length of local + remote). A **line-boundary-preserving union** (`A\n` + `B\n` -> `A\nB\n`, multi-line with shared lines) and a **genuine first write with one side empty** stay clean. **The guard is not applied when both sides contain plugin markers (the orphan-marker self-heal path)**, because self-heal deliberately re-unions content with markers to converge (the nested-marker backstop separately prevents real re-entry). Test: `G3-1` (`tests/a-no-nextcloud/merge/emptyBaseFusion.test.ts`, using the real reconcile-text).
  - Ruling: the old test of `CSF-2` (the contract "**non-conflicting** text edits -> clean") asserted clean for `local` / `remote` with base = '' (independent divergent edits, which are actually a conflict), and so encoded the fusion bug. The contract is unchanged, and the test input was corrected to a **non-conflicting union that preserves line boundaries** (`A\n` / `B\n`). `CSS-12` was corrected to express the deterministic pick with `autoMergeFileStrategy:'remote-win'`, matching the fact that a markdown body always uses `autoMergeFileStrategy` (a behaviour ruling; the meaning of the clause is unchanged).
- **`G3-3`** (`MergeEngine.merge`): fixed a defect where the non-markdown-only entry `merge()` (reached from `ConflictResolver.decideMerge` only when `!isMarkdown(path)`) split a leading `---...---` of a non-md file as YAML frontmatter. A `---` in a non-md file is not guaranteed to be YAML, and when parsing failed `pickWholeSide` could **silently discard a one-sided edit inside that block as a whole**. `merge()` now **3-way merges the whole content as one body** (independent frontmatter and body handling is done only for real markdown, in `resolveMarkdown`). Test: `G3-3` (`tests/a-no-nextcloud/merge/nonMarkdownLeadingDashes.test.ts`). The old HFM-family tests that verified the frontmatter merge by calling `merge()` directly were moved to the production path `resolveMarkdown(..., {frontmatterStrategy:'merge', bodyStrategy:'merge'})` (same behaviour).

## §19. Test traceability

- Classification: `tests/a-no-nextcloud` (pure logic, the default `pnpm test`, CI) / `tests/b1-nextcloud-headless` (real Nextcloud, `bash tests/docker/run.sh b1`) / `tests/b2-nextcloud-ui` (real Obsidian UI on desktop Electron, `bash tests/docker/run.sh b2`) / **`tests/b3-android-ui` (real Obsidian on real Android, `bash tests/docker/run.sh b3`)**. For details see `tests/README.md`.
- **b-3 (the Capacitor runtime layer)**: it covers only behaviour that can be reproduced only on real Android. The subjects are (1) the foreground/background transition of the app (the OS stopping WebView timers), (2) the name-length limit of the real filesystem, and (3) differences in the mobile `requestUrl` implementation. There are only four clauses, `AND-1` to `AND-4`, and each clause carries one sentence on "why a / b-1 / b-2 cannot reproduce it" (a discipline to avoid overlap). **Desktop mobile emulation (`app.emulateMobile`) is no substitute for b-3**: it only switches the UI mode (`Platform.isMobile`) while the execution base remains Electron/Chromium/Node, and it reproduces none of (1) to (3) above. iOS is out of scope for b-3 because the base used is not supported on it, and this stays as a permanent verification gap.
- **Run conditions of b-3**: the single entry point `tests/docker/run.sh b3` starts Redroid (Android is **pinned to API 33**) and Nextcloud (PostgreSQL, Redis, a `files_lock` configuration) on the same Docker Compose (the host needs binder; without it the exit code is 3). The CA generated for each run is installed into the system CA store so that the self-signed certificate is trusted. From API 34 the system CA store moved into an APEX and cannot be installed into, so the version is pinned (covering OS versions is not the purpose of this layer). The operations of N actors go through the `nc-fsops` sidecar, not SSH. It is a **mandatory gate for a beta release (`run.sh all` all green)**, and under `SUITE_REQUIRE_ENV`, environment-caused SKIPs, b-1 included, are treated as failures (a "ran and failed" or "no environment" result is never read as SKIP). A verification failure is not retried, and retries are limited to the environment-preparation stage.
- Each test references a clause of this specification only through a `[SPEC:<id>]` tag (or `spec()`, which generates the same tag); a bare match of a clause ID without the tag does not count as coverage (to prevent false matches against an ID with the same number belonging to another feature). `tests/a-no-nextcloud/spec-coverage/clauses.ts` is the catalog, and `coverage.test.ts` mechanically detects uncovered clauses, typos and waivers.
- **The coverage scan does not count the traceability of skipped tests such as `it.skip` / `describe.skip` / `xit` (the title plus the explanatory comment directly above it) as coverage** (a skip verifies nothing). A comment label attached to an active assertion (for example `// VR-2:` inside the same `it()`) is valid as coverage. Deferred b-1 e2e tests (CN-3, CHK-4, CF-13, CG-10, SF-1, LK-1, LK-3 and so on) are **made explicit by a waiver** and not silenced.
- **When this specification is changed**: (1) update this file with the full current specification, (2) reflect the affected clauses in `clauses.ts`, (3) add or update the matching tests, and (4) turn the coverage checker green with `pnpm test`.

Only a `[SPEC:<id>]` tag (or `spec()`, which emits the same tag) counts as coverage. `DOC-1` verifies that every `docs/spec.md §...` or `docs/plan.md §...` reference in a comment points to a heading that actually exists, and `DOC-2` verifies that comments contain neither a non-public path (the specs directory, the report directory) nor a feature-number history.

## §20. Development toolchain

`eslint.config.mjs` describes itself in its opening comment as "a mirror of the reviewer" (it mirrors the Obsidian community-directory reviewer). The permanent policy for keeping this design intent mechanically is recorded below.

- **The lint gate follows the reviewer's version**: the repository's `eslint-plugin-obsidianmd` is kept equal to the version used by the automatic review of the Obsidian community directory. This prevents a Warning that only the reviewer detects and the repository's pre-push lets through (a divergence caused by a version difference). When the reviewer moves to a newer version in future, re-sync with the same "follow the version" procedure (the axis of the permanent fix is aligning the version itself, not hand-tuning individual rules).
- **`obsidianmd/prefer-create-el` is pinned to `error`**: `obsidianmd/recommended` ships this rule as `warn`, so unless it is explicitly promoted to `error`, pre-push cannot detect a recurrence of `createEl('div'/'span', ...)` (with `warning`, `eslint src` still passes with exit 0). DOM elements that create `div` / `span` in `src/**` must use `createDiv(...)` / `createSpan(...)`. Tags other than `div` / `span` (`p`, `a`, `code` and so on) are outside the rule and may stay `createEl`.
- **The lint rule for the declarative settings API stays off**: `obsidianmd/settings-tab/prefer-setting-definitions` is explicitly `off` in `eslint.config.mjs` (with an explanatory comment). The settings tab itself uses `getSettingDefinitions()` (§15), so this rule is not needed to drive the migration, and the rule's Warning is a non-blocking Recommendation that does not affect the approval status of the review. Advanced custom UI such as the login flow, the live-update banner, the slider plus numeric input and folder suggestions is kept as `render` rows inside the definitions array.
- **Versions of the toolchain and how they are decided**:

| Target | Version | Notes |
|---|---|---|
| TypeScript | **6.0.3 (held)** | 7.x is not adopted. The `ts-jest` peer is `<7`, the `typescript-eslint` peer is `<6.1`, and 7.0 is a Go implementation that **does not bundle the old JS Compiler API** (official wiki: the Compiler API exists up to 6.0, and from 7.1 there is a separate API). - **Keep `minimumReleaseAge` (the pnpm default of 1440 minutes).** "Latest" means "the latest that has been public for at least one day". In an actual update, `@wdio/*` 9.31.7 and `typescript-eslint` 8.70.0 were not chosen because they had just been published.
- **Future candidate (not adopted)**: `pnpm/setup@v1` can install pnpm and Node in one step and could replace `actions/setup-node`, but it was passed over because it exceeds the scope of that update (raising versions).
- **Classification of production and development dependencies**: a dependency that is not imported from production `src/` is placed in `devDependencies`, not `dependencies`. **`js-yaml` is not a direct dependency at all** (neither `dependencies` nor `devDependencies`, and no `@types/js-yaml`): the community-directory reviewer flags it as a package to replace. Production parses frontmatter with Obsidian's `parseYaml` / `stringifyYaml` (HFM-1), and the test doubles of those two functions use `yaml`. The doubles call `stringify` with `version: '1.1'`, `singleQuote: true` and `lineWidth: 0`, which reproduces the earlier js-yaml output byte for byte (YAML-1.1-ambiguous scalars such as `yes` and dates are quoted, no line folding). `parse` takes no options, so `yes` / `on` stay strings. `js-yaml` still arrives transitively (istanbul / secretlint / mocha), so the `pnpm-workspace.yaml` override above stays. Tests: `SWC-1` to `SWC-5` (`tests/a-no-nextcloud/spec-coverage/clauses.ts`), and the pinned double output under `HFM-14`.
